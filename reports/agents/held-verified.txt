#1 [major, confidence medium] Main scope lens is never hidden by sight mode, and per-mode lenses are disabled for that weapon
VERDICT: CONFIRMED
Reason: The branch is taken at construction. HeldWeapon.cs:119 calls VRScope.Wanted, which returns true when Sights.Length > 1 and GetAimFov() < 40 (VRScope.cs:47). GetAimFov depends on the active sight mode (decompiled Weapon.cs:2446-2456), so a weapon drawn in a magnified mode takes the _scope branch (HeldWeapon.cs:121). The else branch that creates _modeScopes (HeldWeapon.cs:123-126) is skipped. UpdateModeScopes (HeldWeapon.cs:1012-1036) runs every frame (called at 1007) but returns at 1014 because _modeScopes is null, so the mode lenses are never created. _scope is never passed to SetShown: the only SetShown call is on _modeScopes (1029), and _scope is referenced only at 121, 1005 and 1879. VRScope._shown defaults to true (VRScope.cs:27), and BeforeRender draws the dark lens disc (color 0.05) even when not aiming (VRScope.cs:246-250). Line correction: the early return that causes the bug is at HeldWeapon.cs:1014, not 1005.
Trigger: A weapon with Sights.Length > 1 is drawn while its selected sight mode is magnified (GetAimFov() < 40). The player then switches to an unmagnified mode (red dot or iron).
Effect: The main scope's dark ocular disc (and the magnified picture while aiming) stays visible in every sight mode, sitting over the red dot or iron sight. It is never hidden for the rest of that weapon's hold.
Fix idea: Create _modeScopes whenever Sights.Length > 1 (not only in the else branch), and gate the main _scope with SetShown(selected mode is Magnified), or construct the lens per mode and drop the construction-time choice in Wanted.

WeaponSystem.cs:296-305 sets Held = null in the catch without calling Release(), and GunCollider.Create (HeldWeapon.cs:135; GunCollider.cs:479-491) sets the static Current and makes a DontDestroyOnLoad object. No concrete reachable exception was found, so the stated trigger ("any exception after 121 or 135") is not a demonstrated defect. Treat it as a hardening item. Line note: GunCollider.Current is assigned at GunCollider.cs:491, not 490.

#3 [minor, confidence low] Slide is not returned to rest when its offset drops to zero (only the handle is reset)
VERDICT: UNSURE
Reason: The mechanics are real but the visible effect depends on whether the animator drives the slide. ApplyPartOverrides (HeldWeapon.cs:1646-1654) moves Rig.Slide only while SlideOffset > 0.0005, and the else branch resets only Rig.Handle. Rig.Slide is written only at 1648 and 1796 (Release). The one-frame drop is real: ReloadInteractions.cs:1489 uses MoveTowards(SlideOffset, 0, 6*dt) with dt capped at 0.05 s, and SlideTravel is clamped to 0.02-0.15 m (WeaponAnalyzer.cs:1056), so at 60 fps a slide with travel up to about 0.1 m jumps from full travel to 0 in one step. ApplyPartOverrides runs before Reload.BeforeRender in the same frame (HeldWeapon.cs:991 and 1003), so the last write is the pulled-back position. Line correction: 2393 and 2503 are doc comments, not assignments. The zeroing sites are ReloadInteractions.cs:1498 (the !_racking branch), 2495, and 2605. The effect is masked when the game's animator writes the slide each frame. The analyzer finds slide parts by sampling the animator (WeaponAnalyzer.cs:1054, and the comment at HeldWeapon.cs:655-660 says the animator runs the slide). Only manually overridden slides (WeaponOverrides.cs:106-113) with no animator motion would show the stuck slide, and no such case was verified. Severity should be low, not minor, unless such a weapon is confirmed.
Trigger: Bolt or slide pulled back, then SlideOffset falls to 0 in one step while the weapon is held.
Effect (if not animator-driven): Rig.Slide stays at its last pulled-back pose until release or the next rack.
Fix idea: In the else branch, also call MovePart(Rig.Slide, d.SlideRestLocal, Vector3.zero), but only if the slide is not animator-driven, to avoid fighting the animator.
