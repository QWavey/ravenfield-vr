#1 [minor] [confidence medium] Evicted gun volumes leave their hull Meshes alive; every rebuild after eviction adds another set
   where: src/Weapons/GunVolume.cs:282-288 (LRU eviction), with the Mesh created at src/Weapons/ShapeFit.cs:34-36
   trigger: the player holds more than 12 distinct held-weapon types in one session (GunVolume.CacheSize = 12, GunVolume.cs:24). The 13th volume evicts the least recently used one, and holding that weapon type again rebuilds the volume.
   effect: the evicted volume HullPieces (ShapeFit.Piece objects, up to HullMaxPieces = 16 per volume, GunVolume.cs:78) each own a lazily created UnityEngine.Mesh named "RavenfieldVR hull". Nothing destroys those Meshes. GunCollider.Destroy (GunCollider.cs:842-853) destroys only its GameObject, and the Piece and GunVolume objects are plain C# objects that the GC collects without releasing the native Mesh. Each rebuild that feeds the new pieces to a collider creates a fresh set of hull Meshes, so one set stays in native memory per eviction-and-redraw cycle for the rest of the session.
   evidence: GunVolume.Cached (GunVolume.cs:257-290) removes evicted entries from Cache and CacheOrder and destroys nothing. GunVolume.cs:554-557 builds HullPieces with ShapeFit.FitCloud on every build. HeldWeapon.cs:1076 calls GunVolume.For once per HeldWeapon (guarded by _volumeTried). GunVolume.For sets WantsHull = true (GunVolume.cs:227), so every held weapon volume gets HullPieces. The only creator of these meshes is ShapeFit.Piece.Mesh (ShapeFit.cs:27-51, new Mesh at line 36), reached from ShapeFit.AddColliders (ShapeFit.cs:603-605), which GunCollider.UseShape uses (GunCollider.cs:393). HeldWeapon.cs:1221, 1228, 1236 and 1249 are the callers. No code path destroys a Piece mesh: ShapeFit.cs:611 DestroyImmediate targets the collider, and ShapeFit.ClearCache (ShapeFit.cs:648) has no caller.
   fix idea: give GunVolume a Release that destroys the Mesh of each HullPieces entry when the volume leaves the cache (or when no collider uses it any more). Alternatively keep the hull meshes in a bounded cache keyed by weapon key, as ShapeFit.Cache already does for held keys, and reuse them on rebuild.

#3 [minor] [confidence low] Grenade dud copies of skinned models leak their baked Mesh on every throw

#4 [tiny] [confidence low] Fallback box shape allocates a new hull Mesh on every draw when nothing is measurable
   where: src/Weapons/GunCollider.cs:534-540 (fallback piece), 489-491 (Create), src/Weapons/ShapeFit.cs:36 and 603-605 (AddColliders creates the mesh); the same pattern at src/Weapons/GrenadeDud.cs:66-70
   trigger: GunCollider.Fit keeps no pieces: the cached held pieces are empty (ShapeFit.Fit returns an empty array when fewer than 8 points are measured, ShapeFit.cs:92), or every piece lies outside the envelope (GunCollider.cs:528-531). The same happens for a dud whose dud fit is empty.
   effect: ShapeFit.BoxPiece returns a new, uncached Piece with 8 points, and AddColliders gives it a MeshCollider with a fresh Mesh because Points.Length is at least 4 (ShapeFit.cs:599-605). Each draw of that weapon type therefore creates another Mesh and another cooked hull that is never released.
   evidence: VisibleRenderers (GunCollider.cs:557-580) returns only enabled renderers, so the empty case is reachable for a weapon whose measurable meshes are all disabled. I did not confirm a shipped weapon that reaches this state.
   fix idea: cache the fallback piece under its own key so its Mesh is made once, or add the fallback as a plain BoxCollider when there is no mesh to cook.
