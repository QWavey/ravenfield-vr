[minor/medium] src/Rig/IntroStage.cs:75  Intro title scan stops about 0.65 s into the intro (pre-existing, not in the window)
  what:   IntroStage.Update runs PlaceTitleInWorld only under 'if (_isIntro && _phase != Phase.Done && Time.unscaledTime >= _nextTitleScan)' (IntroStage.cs:75). Phase goes Idle, then Measuring (0.25 s, line 137), then Verifying (0.4 s, line 147), then Done (lines 116, 142, 166). The comment at line 77 says the scan exists for 'Text that switches on later in the intro too'.
  why:    After about 0.65 s the scan stops. Canvases that appear later stay screen-space, the HUD conversion makes them head-locked, and they are drawn over the walkers. That is the case this file exists to prevent, since the walkers are placed in front of the view (IntroStage.cs:217-226). No commit in the window touches this file, so this is not a regression from the recent changes.
  change: Gate the title scan on the scene being the intro (_isIntro) instead of on _phase != Done, keeping the 0.1 s throttle. Keep the Done gate for the walker steps only. Note that the scan runs two scene-wide FindObjectsOfType calls (lines 278, 317) for the whole intro, so stop it once the intro scene ends.

[minor/low] src/Rig/LensEffects.cs:160  LensEffects publishes Instance before it is fully built
  what:   LensEffects ctor sets 'Instance = this;' on its first line (LensEffects.cs:160), while '_ok = true;' is the last line (212). VRRig wraps the ctor in try/catch (VRRig.cs:110-117, added in 9db2f56) and leaves _lens null on a throw. The no-shader path returns early with _ok false (LensEffects.cs:164-168) but still leaves Instance set.
  why:    With no additive shader, LensFlash.TryFlash sees a non-null Instance and calls fx.AddFlash every shot (LensFlash.cs:198-199, 258-260; LensEffects.cs:258-262). Pruning happens only in Present() (LensEffects.cs:330-382), which returns at 316-318 while _ok is false, so _flashes grows for the whole session. After a ctor throw, _lens stays null, so Dispose's _lens?.Destroy() (VRRig.cs:1058) does nothing. Instance is never cleared and the threads started at LensEffects.cs:202-211 are never stopped.
  change: Move 'Instance = this;' from LensEffects.cs:160 to just before '_ok = true;' (line 212). In AddFlash (line 258) return early when !_ok. A half-built or no-shader LensEffects is then never published, and every caller already handles a null Instance (LensFlash.cs:199, the ?. calls in DamageFeedback.cs and MudSplash.cs).

[minor/low] src/Rig/VRRig.cs:1086  Scripted platform yaw bypasses the new wheel/stick turn gate
  what:   ScriptedRotationPatch.Prefix calls rig.AddYaw(input.x) with no check (VRRig.cs:1086). The gate added in 9167a24 (VRRig.cs:493-496, 'allowed &= !(Hands[0] ... The game calls MouseLook.ApplyScriptedRotation from FirstPersonController.UpdateMovingPlatform (.ref/decompiled/firstpass/UnityStandardAssets.Characters.FirstPerson/FirstPersonController.cs:322) whenever the player stands on a rotating platform.
  why:    If a seated player is carried round by a rotating platform while a hand holds the wheel or flight stick, AddYaw (VRRig.cs:538-547) adds to _seatYawOffset and turns the rig about the eyes. That is the hand swing 9167a24 blames for the phantom steering: the palm moves about 30 cm round the head while the car's rim does not. I did not confirm that a seated player is ever under this platform yaw.
  change: In ScriptedRotationPatch.Prefix, after the VRGameInput.Enabled check, return false without calling AddYaw while rig.Hands[0].Role or rig.Hands[1].Role is HandRole.Cockpit. Or put the same Cockpit check inside AddYaw for the Anchored branch.
