[major/medium] src/UI/CanvasManager.cs:429  Game camera aspect follows whichever visible canvas came last
  what:   `float aspect = 16f / 9f;` (419), then inside `foreach (Tracked t in _tracked.Values)` for every visible canvas, menus and collimated sights included: `if (t.Size.x > 1f && t.Size.y > 1f) aspect = t.Size.x / t.Size.y;` (429). That value sets `player.fpCamera.aspect = aspect` and the vertical FOV (455-459). The comment at 454 says the camera must match the HUD frame.
  why:    Dictionary order decides which canvas wins, and with no visible canvas the camera falls back to a fixed 16:9. So the camera's FOV changes whenever the visible set changes between screen-sized canvases and anything else. A visible canvas with its own size (a menu popup, or a square gunner reticle at 80 m) takes the camera aspect of that canvas. With HudHorizontalFov 72 (VRConfig.cs:301), aspect 1.0 gives a vertical FOV of 72 deg instead of 44.4 deg at 16:9, and screen-projected markers (objectives, squad orders) move off their world targets. A non-16:9 window produces the same jump against the 16:9 fallback.
  change: Compute the camera aspect once per frame from one fixed source (Screen.width / Screen.height, or only the head-locked non-collimated HUD canvas), never from Menu or Collimated canvases. Take `aspect` out of the per-canvas loop. For HUD frames, use a non-uniform scale so each canvas fills the frustum regardless of its own size: localScale = (width / Size.x, width / aspect / Size.y, 1).

[major/low] src/UI/VRInputModule.cs:115  Click target comes from every GraphicRaycaster, not only the menus
  what:   `eventSystem.RaycastAll(_data, _results)` (115) runs every raycaster in the scene, including the head-locked HUD frames (their WorldSpace canvases use _eventCamera as worldCamera, CanvasManager.cs:207). `over = first.gameObject` and `VRGameInput.PointerOverUI = over != null` (119-120) come from that unfiltered list. The laser's own target is intersected only against Targets (IntersectCanvases, 175-207). The repo sets blocksRaycasts only on the match bar (CanvasManager.cs:364) and turns off raycasts nowhere else.
  why:    A HUD frame graphic with raycastTarget on (Unity's Image default), lying on the laser and sorting ahead of the menu, takes hover, press and click, so the menu button under the laser does not respond. PointerOverUI is also set from HUD graphics, and in menus that blocks fire (GameInputBridge.cs:121). The match bar needed a special case for this, so the same interference is plausible for other HUD canvases. Whether the game's HUD graphics are raycast targets is in asset data not in the repo, so this is unverified.
  change: After RaycastAll, skip any result whose `(res.module as GraphicRaycaster).canvas.rootCanvas` is not one of Targets. Alternatively, in CanvasManager.Update, set GraphicRaycaster.enabled = false on HUD-role canvases when their role changes and re-enable them on Menu.

[minor/low] src/UI/CanvasManager.cs:127  Canvas that turns Menu while already visible skips the flatten pass
  what:   `if (opening && t.Role == CanvasRole.Menu) { t.Placed = false; CollectFlat(t); }` (127-131). `opening` is `visible && !t.Visible` (118). The role is recomputed separately when `gameplayChanged` flips (119-125).
  why:    A canvas that is already visible as HUD during play and has a clickable element becomes a Menu when the game menu opens. It is not `opening`, so CollectFlat never runs for it and its nested pages keep their depth, which is the failure the comments at 221-225 and 296-300 describe for the options pages. The trigger needs a visible HUD canvas with an interactable when the game menu opens.
  change: Keep the previous role on each Tracked entry and run the menu-open block (Placed = false, CollectFlat) whenever the role becomes Menu, not only when the canvas becomes visible.

[minor/medium] src/UI/CanvasManager.cs:156  First open of a game menu shows flat for up to 0.4 s
  what:   Scan() uses `UnityEngine.Object.FindObjectsOfType<Canvas>()` (156), which returns only active objects, and runs at most every 0.4 s (95-98). ScanNow() is called only from WeaponListShowPatch.Postfix (656-661), for the loadout list.
  why:    A game menu that was inactive at the last scan and is opened for the first time is drawn by the game as a screen-space canvas (flat in the headset) until the next scan converts it, up to 0.4 s later. The comment at 392-395 describes exactly this flash for the loadout list, which is the only menu with a hook.
  change: Call CanvasManager.ScanNow() from Harmony postfixes on the other menu-open methods (pause menu, options, squad map, scoreboard), or detect a root canvas that has just become active each frame, for example by caching the root canvases and refreshing on activation.

[minor/high] src/UI/CanvasManager.cs:436  HUD frame sized for one distance but placed at another
  what:   `float width = 2f * d * Mathf.Tan(...)` and `float scale = width / t.Size.x;` (435-436) use d, while `float depth = d - 0.001f * d / distance * Mathf.Clamp(t.Order, -100, 100);` (437) places the frame at `hud.Forward * depth` (438).
  why:    A canvas with sortingOrder 100 at the default HudDistance of 4 m (VRConfig.cs:299) sits 0.1 m closer than its size assumes, so its frame subtends 4/3.9, about 2.6% more than the camera frustum, and markers on it stop lining up with world targets. Collimated sights show the same 2.6% (80/78). The error grows with |Order|. The sortingOrder values the game uses are not in the repo, so the size of the effect is unverified.
  change: Size the frame at the depth it is placed at: move the depth line above the width line and use `float width = 2f * depth * Mathf.Tan(hfov * 0.5f * Mathf.Deg2Rad);`.

[minor/medium] src/UI/UISystem.cs:148  Trigger press that switches the pointer hand never clicks
  what:   UISystem.Update moves `_pointerHand` when `_module.TriggerPressed(other)` (148). TriggerPressed returns `_triggerPressed`, which changes only inside VRInputModule.Process via UpdateTriggers (VRInputModule.cs:63-76). Process takes its `press` (122) from `_triggerPressed[(int)PointerHand]`, the hand the laser is on.
  why:    The other hand's press edge is consumed by Process while the laser is still on the old hand, so nothing is clicked. On the following frame the hand switches, but Process recomputes `_triggerPressed[other]` as false because the trigger is still held and there is no new edge. The pull that moves the laser to the other hand clicks nothing, and the user has to pull again.
  change: Let the switch and the click use the same edge. In VRInputModule.Process, right after UpdateTriggers and before `press` is computed, set PointerHand = other when `_triggerPressed[other]` is true and the other hand is tracked (UISystem supplies that tracked state). Keep UISystem only for the initial hand and the lost-tracking fallback.

[minor/low] src/UI/UiKit.cs:62  UI font fallback is cached for the whole session
  what:   The `Font` getter (24-36) caches FindGameFont's result. FindGameFont returns `Resources.GetBuiltinResource<Font>("Arial.ttf")` (62) when no non-Arial Text is loaded. That value is non-null, so `_font` is never retried.
  why:    The first MakeText runs inside VRSettingsPanel's constructor (VRSettingsPanel.cs:43-49, Build -> Label -> MakeText). That constructor runs in UISystem's constructor at VR start (VRManager.cs:62-64), before the game's menu UI exists. If no non-Arial font is loaded at that moment, every mod panel uses Arial for the whole session, although the class summary promises the game's font.
  change: Cache only when a game font was found. Return the built-in fallback without storing it in _font, so the next access retries FindGameFont.
