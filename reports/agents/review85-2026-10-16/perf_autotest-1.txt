SCOPE: Performance review of the autotest first half (src/Core/AutoTest.cs lines 1-1700), src/Core/Shots.cs and src/Core/EyeFilm.cs, all read in full. None of this runs in a normal player session: every path is gated by -rfvr-autotest, -rfvr-shots, -rfvr-flashfilm or -rfvr-perf. The findings are about the harness's own per-frame and per-picture cost, and whether the numbers it reports can be trusted against the 11 ms budget. Costs marked estimate are not measured. The m4a1 ACOG question in the user's message is outside this read-only review and was not checked.

[major/medium] src/Core/AutoTest.cs:94  Picture and film frames count in the frame-time stats the autotest reports
  what:   `PerfProbe.Enabled = true;` (94). PerfProbe.Frame() runs in VRManager.Update (src/Core/VRManager.cs:139) and adds Time.unscaledDeltaTime for every frame. Only MenuTest excludes the frame that took a picture: "the frame a picture was taken in carries its cost ... not the menu's" (AutoTest.cs:162-166). Run() calls PerfProbe.Reset() and then runs weapon checks that take pictures (290-291, 329-330; e.g. LensBurstCheck at 1033, PassHandCheck at 1375).
  why:    The frame p50/p95/max and the 'frame' line of the report include picture and film hitches of tens of ms (see finding 4 and EyeFilm's own work), so they overstate the game's frame cost. Guard sections are not affected, because pictures sit outside them. The user compares these numbers against the 11 ms budget, so the overstatement changes that comparison.
  change: Add PerfProbe.SkipFrame(), which makes the next Frame() skip its sample. Call it after each Shots.Capture and each filmed frame, generalizing the MenuTest afterShot pattern. Alternatively, record harness frames separately and report both figures.

[major/high] src/Core/EyeFilm.cs:151  Film allocates and copies a ~1 MB array on the main thread for every eye frame
  what:   Inside AsyncGPUReadback.Request(rt, 0, TextureFormat.RGBA32, req => {...}) (lines 145-160): `var rgba = new byte[w * h * 4];` (151) then `NativeArray<byte>.Copy(data, rgba, rgba.Length);` (152). The lambda is allocated per OnPostRender (145), and `path` is built per frame (140) with a `Time.unscaledTime.ToString("0.0000")` string (142).
  why:    The film runs OnPostRender for both eyes at up to 90 Hz, about 180 callbacks a second. Each allocates about 1 MB (480 x ~530 x 4 bytes; the close-up camera's 480 x 360 x 4 is about 0.7 MB). That is above the 85 KB large-object threshold, and it is zeroed and copied on the main thread. Estimate: 0.3-0.4 ms per eye, so roughly 0.6-0.8 ms of the 11 ms budget per filmed frame, before GC. The large-object churn (~180 MB/s) makes main-thread full collections more frequent during the film, which the header at EyeFilm.cs:14-16 says keeps the frame rate.
  change: Keep a lock-guarded Stack<byte[]> pool of w*h*4 arrays: take one in the callback and have WriterLoop return it after ImageConversion.EncodeArrayToPNG. Or allocate one Allocator.Persistent NativeArray<byte> per film and copy into it. Cache the readback delegate in a field, and pass the frame number and eye in the queue tuple so the path string is built on the writer thread.

[major/medium] src/Core/EyeFilm.cs:155  Frame queue is unbounded and Finish can freeze the main thread for 15 s
  what:   `_queue.Enqueue((path, rgba, w, h));` (155) with no limit. Finish waits up to 120 s for Queued to reach 0 (lines 85-88), then runs `if (!_writer.Join(15000))` on the main thread (line 91).
  why:    Each queued frame holds about 1 MB, and frames arrive about every 5.5 ms (two eyes at 90 Hz). One writer thread PNG-encodes each. If encoding is slower than that (not measured, and plausible for 480 x 530 RGBA), the queue grows through the film. The comment at lines 83-84 says a machine-gun magazine is about 1400 pictures, which would be up to ~1.4 GB if the writer lags the whole time. If the writer is still busy when the 120 s wait ends, Join(15000) blocks the main thread for up to 15 s and the headset freezes.
  change: Cap the queue: when _queue.Count >= 64, drop the frame, count it, and write the drop count to frames.txt. Replace the blocking Join with a coroutine loop before the final write, e.g. `for (float until = Time.realtimeSinceStartup + 15f; _writer.IsAlive && Time.realtimeSinceStartup < until;) yield return null;`. Record the peak queue depth in frames.txt so writer lag is visible.

[minor/high] src/Core/AutoTest.cs:880  Reload film renders the whole world again on every frame of the pull
  what:   ReloadInteractions.ReloadFilm calls `frame(note)` on every frame of the pull and insert (src/Weapons/ReloadInteractions.cs:2024). The callback (AutoTest.cs:876-881) calls `cam.Render()` (880) on a camera made with `cam.CopyFrom(rig.Camera)` (856) and the full culling mask (858). EyeFilm.Begin(cam, dir, true) (862) then reads each frame back.
  why:    Each frame of every magazine pull and insert gets a second full-scene render (culling, shadow passes and all draws). Those frames therefore cost roughly twice what the game's frames do (estimate), so the reload film's frame timings are not representative. Each frame also allocates a ~0.7 MB readback (finding 1).
  change: Restrict the film camera's cullingMask to the gun and magazine layers, which is all the close-up needs, and mark these frames as harness frames (finding 3). Check the picture afterwards, because removing the background changes what the film shows.

[minor/high] src/Core/Shots.cs:79  Each picture re-renders the scene, stalls on ReadPixels and PNG-encodes on the main thread
  what:   Per call: `go = new GameObject(...)` (62), `rt = new RenderTexture(1280, 800, 24)` (73), `tex = new Texture2D(...)` (75), `cam.Render()` for each pose (79), `tex.ReadPixels` (83, synchronous GPU readback), `File.WriteAllBytes(file, tex.EncodeToPNG())` (95). CaptureFirstClear renders up to five poses in a row while Flat rejects (76-93), and MagazineSideShot passes five candidates (AutoTest.cs:1096-1116). Flat (126-143) calls GetPixel 768 times per pose.
  why:    Each picture is a full extra render of the world at 1280 x 800, a stalled GPU readback and a ~3 MB PNG encode, all in one frame. Estimate: tens of ms per picture. LoadShots takes 90 of them during loading (AutoTest.cs:128-139). EyeFilm already does the same job asynchronously (EyeFilm.cs:145-160), so the pattern is already in the codebase.
  change: Create the capture camera and RenderTexture once per run and reuse them, destroying them at the end. Read back with AsyncGPUReadback.Request as EyeFilm does, and encode on a worker thread with ImageConversion.EncodeArrayToPNG. Run Flat on the readback bytes rather than 768 GetPixel calls. This moves the main-thread cost out of the picture frame.
