[major/high] src/Weapons/ReloadInteractions.cs:1078  Loose rocket capture uses the near end's depth as the tip's depth
  what:   LooselyLined (lines 1156-1162) picks whichever end is nearer the mouth (`Vector3 near = ... ? a : b;` with a = TipLocal, b = BaseLocal) and returns `depth = Mathf.Max(0f, Vector3.Dot(rel, insert))` for that end. The capture block (1078-1085) then does `prop.RailHandOffset = along - looseDepth; ... along = looseDepth; ... prop.RailDepth = Mathf.Clamp(along, 0f, prop.RailLength);`, but `along` comes from HandAlongRail (1174-1181), which measures only TipLocal (the tail). The depth used for the tail is the base's depth whenever the base is nearer.
  why:    When the warhead (base) end is nearer the mouth, RailDepth is set to the base's depth, not the tail's. The tail is pulled toward the muzzle by (tail depth - base depth), at least half a rocket length under the 60-degree test. ShowOnRail (1704) draws the rocket there and HeldPalm moves the glove with it. The OnRail setter eases only over 0.08 s (MagazineProp.cs:94-113), so the rocket and hand visibly jump out of the tube front on capture. This is the front-loading case the user asked about. Introduced in d077bdd. Note: this is in the first half of the file, outside my range, but it sits on the rocket path the film tests.
  change: In LooselyLined, return the depth of the end HandAlongRail measures: `depth = Vector3.Dot(a - mouth, insert);` (the caller already clamps RailDepth at 1085). Keep `near` only to decide which end passes the line-up test. Add a film check that RailDepth does not change across the capture frame (within 1 cm).

[minor/medium] src/Weapons/ReloadInteractions.cs:1447  Charging-handle stroke lost its 3 cm floor; short handles rack on a 1.5 cm pull
  what:   `private float StrokeLength => HandleStroke ? Data.HandleTravel.magnitude : Travel;` Commit 0df7b82 replaced `Mathf.Clamp(Data.HandleTravel.magnitude, 0.03f, 0.14f)` with this. HandleStroke only needs travel over 1 cm (line 1443). The analyzer keeps a charging handle whose travel is at least 1.5 cm (WeaponAnalyzer.cs:1815, `if (back < 0.015f || ...) continue;`) and stores it as HandleTravel (WeaponAnalyzer.cs:1170).
  why:    UpdateRack maps hand pull to action position with `pull / StrokeLength` (lines 1517-1518). For a 1.5 cm handle the action moves twice as far per centimetre of hand as before. The rack-back threshold (fraction >= 0.8, line 1534) is reached after about 1.2 cm of pull instead of 2.4 cm. Removing the 14 cm ceiling was the intended fix for long handles; the 3 cm floor was not meant to go.
  change: `private float StrokeLength => HandleStroke ? Mathf.Max(Data.HandleTravel.magnitude, 0.03f) : Travel;` This keeps the uncapped top that 0df7b82 wanted.

  what:   `Vector3 handAt = off.Model != null ? off.Model.GraspPointWorld : RackPointWorld;` GraspPointWorld is set from `target` before the settle offset and keep-out are applied (HandModel.cs:580), but the glove is drawn at `target.position + _graspOffset + _keepOut` (HandModel.cs:604).
