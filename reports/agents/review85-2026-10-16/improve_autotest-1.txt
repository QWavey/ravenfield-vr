[major/high] src/Core/AutoTest.cs:183  Frame budget hard-coded to 90 Hz; hides dropped frames on 120 Hz
  what:   `int over = frames.Count(f => f > 1000f / 90f + 1f);` (AutoTest.cs:183), with the report saying "over the 90 Hz budget" (line 187). OpenVRRuntime.cs:115 already logs the real `XRDevice.refreshRate`.
  why:    On a 120 Hz headset a frame over 8.3 ms drops a frame, but this counts only frames over 12.1 ms. Frames of 8.5-12 ms, which judder the view, are counted as fine, so the menu test can report zero over budget while the player sees judder. Judder is a comfort problem in VR. On a 72 Hz headset the count is overstated the other way.
  change: Replace the constant with `float hz = Mathf.Max(30f, UnityEngine.XR.XRDevice.refreshRate); float budgetMs = 1000f / hz;`, use `f > budgetMs + 1f` at line 183, and print `{hz:0} Hz budget` at line 187.

[major/high] src/Core/AutoTest.cs:931  Rocket film's TOO SMALL verdict never fails the run

[minor/high] src/Core/AutoTest.cs:186  Menu-view drift is printed but never fails the menu test
  what:   drift and turn are measured per frame (AutoTest.cs:169-170). The only output is `View moved: ... (should be 0: ...)` (line 186), written to RavenfieldVR-menutest.txt (line 192). No threshold, no Problem, no FAIL line.
  why:    A menu camera that drifts or turns while the player stands still makes VR motion sickness. A run with 30 cm of drift and a clean run end the same way; the only signal is a number someone has to read by hand. Problems is only written by Write(), so the menu test cannot raise a problem through it.
  change: After the loop, when `drift > 0.01f || turn > 1f`, add a line starting "FAIL:" to sb (and a Log.Warn), so the file itself carries the verdict. Keep the numbers.

[minor/medium] src/Core/AutoTest.cs:1259  Held-still thresholds are per frame, so the verdict depends on frame rate
  what:   `bool shaky = maxA > 0.2f || maxM > 0.002f;` (AutoTest.cs:1259). The samples are taken once per frame after `yield return new WaitForEndOfFrame();`: `angles.Add(Quaternion.Angle(lastRot, body.rotation)); moves.Add(Vector3.Distance(lastPos, pos));` (lines 1280-1281).
  why:    The same steady hand gives proportionally more motion per frame at a low frame rate. The wrist test notes runs at 12 fps, and at that rate ordinary sway can fail as "SHAKES". At 120 Hz real shake can pass under 0.2 deg per frame. The pass/fail therefore means different things on different machines.
  change: Divide each sample by Time.unscaledDeltaTime and compare in per-second units: 0.2 deg per frame at 90 Hz is 18 deg/s, and 2 mm per frame is 0.18 m/s. Print the run's frame rate in the line at 1289/1299 so a failure can be read against it.

[minor/high] src/Core/EyeFilm.cs:21  Reload close-up is downscaled to 480 px wide before it is saved
  what:   The close-up camera renders into `new RenderTexture(640, 480, 24)` (AutoTest.cs:895). EyeFilm uses `private const int Width = 480;` (EyeFilm.cs:21) and `int w = Width, h = Mathf.Max(2, Mathf.RoundToInt(Width * (float)sh / sw));` (EyeFilm.cs:132), so mono frames are saved at 480x360.
  why:    The close-ups the user needs for comparing magazines and rockets lose a quarter of their width before saving. Small parts such as a rocket's nose or the seat lose the detail needed to tell two models apart.
  change: In EyeFilm.OnPostRender use the camera's own width for mono films: `int w = _mono ? _cam.pixelWidth : Width;` (keep h derived from sh/sw). That keeps the 640 px close-ups at full size.
