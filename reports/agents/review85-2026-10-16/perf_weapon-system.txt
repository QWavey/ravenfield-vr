SCOPE: Read-only per-frame and frame-spike review of the seven listed weapon files (WeaponSystem, WeaponPatches, WeaponRig, WeaponOverrides, WeaponWarmup, FireSelector, Casings), plus the helpers they call on hot paths (GameContext, BodyZones, AmmoState, MagazineProp, WeaponDrops, ShapeFit, VRHand, ProceduralSounds, decompiled Weapon/Actor/GameManager). [major/high] src/Weapons/WeaponWarmup.cs:145  Warm-up runs a whole weapon's analysis, shape fit and drop copy in one frame
  what:   Lines 145-168: the try block calls WeaponAnalyzer.Get(weapon, entry) (148), PrefitShape(weapon, data) (149), WeaponDrops.Prepare(entry) (150-153) and WeaponAnalyzer.Get for every sub-weapon (154-160) back to back with no yield between them. The pacing at 171-175 (rest = Clamp(CeilToInt(elapsed/6), 1, 45) empty frames) is computed after the work, so it only spaces frames out and never splits the spike. The file itself says one analysis takes tens of milliseconds (lines 10-11, 169-170), PrefitShape fits tens of thousands of vertices (37-39), and WeaponDrops.cs:179-181 says copying the third-person model costs tens of milliseconds.
  why:    In the menu, every catalog weapon not yet cached produces one frame equal to the sum of its stages, plausibly 50-150 ms (estimate, not measured) against an 11 ms budget at 90 fps. That is several dropped frames per weapon, repeated across hundreds of catalog weapons while the menu is up, and it is the kind of long single stall that looks like a hang. InMatch() is checked only before the entry (121-124, 134-137), so a match that starts while an entry is in flight takes the whole stall at match start. Not confirmed at runtime.
  change: Give each stage its own frame: yield return null after WeaponAnalyzer.Get(weapon, entry), after PrefitShape, after WeaponDrops.Prepare, and after each sub-weapon Get. Check InMatch() before each stage. Keep per-entry progress in a small local state so Warmed.Add (162) runs only once every stage is done. Keep the rest-frame pacing so the average stays near 6 ms.

[minor/high] src/Weapons/WeaponDrops.cs:738  Every frame both free hands scan every collider of every dropped weapon
  what:   WeaponDrops.Update (556-595) runs every frame, called from WeaponSystem.Update (src/Weapons/WeaponSystem.cs:137). For each tracked hand that can grab, line 581 runs DroppedWeapon near = canGrab ? Nearest(hand.Palm.position) : null with no grip gate. Nearest (734-752) loops every drop and every collider: float dist = c != null ? Vector3.Distance(c.ClosestPoint(palm), palm) : float.MaxValue; with no bounds pre-check. The colliders are convex MeshColliders, one per fitted piece (src/Weapons/ShapeFit.cs:603-604; maxPieces defaults to 16 at ShapeFit.cs:78 and 113). Drops are capped at MaxDroppedWeapons = 16 (src/Core/VRConfig.cs:291).
  why:    With the cap reached, up to 16 drops x 16 pieces x 2 hands = 512 ClosestPoint calls every frame while on foot, whether or not a hand is near anything or the grip is pressed. Unmeasured estimate: roughly 0.3-1 ms a frame, about 3-9% of the 11 ms budget. The cost grows with the number of drops, so it builds up over a long match.
  change: Add a broad phase per drop. Cache each drop's world bounds centre and radius at spawn and refresh them only when the drop moves (drops mostly rest). Skip a drop before the collider loop when (palm - centre).sqrMagnitude > (radius + PickupReach)^2. A convex collider's closest point lies inside its bounds, so grab results for near drops are unchanged. Alternatively run the search only when the hand is within about 1 m of a drop's root position.

[minor/medium] src/Weapons/WeaponPatches.cs:136  Each draw steps the animator 25 times, then 25 more on the next frame
  what:   Lines 90-91: Steps = 25, StepSeconds = 0.1f. The Postfix calls Step(anim) (108) and starts StepNextFrame (112), which calls Step(anim) again on the next frame (126). Step runs anim.Update(StepSeconds) in a 25-iteration loop (136-139) with fireEvents off.
  why:    That is 50 full Animator evaluations per draw, each advancing 0.1 s of simulated time, split across two consecutive frames on the main thread. Cost per Update is not measured; estimate 0.05-0.2 ms each for a weapon with a skinned arm rig, so roughly 1-5 ms per spike frame. The player feels this as a hitch on the draw frame and the one after.
  change: Measure how many steps the state actually needs: after each anim.Update, log anim.GetCurrentAnimatorStateInfo(0).shortNameHash and anim.IsInTransition(0) once. Then cut the loop to that count plus a margin, or break early once the state stops changing. Keep the frame-two step only if the first step was skipped.

[tiny/medium] src/Weapons/Casings.cs:80  Casing pool starts empty on each map, so the first casings are built in shot frames
  what:   Drop() spawns up to 8 casings in one call (line 80: i < Mathf.Min(count, 8)). Spawn takes from the pool or calls Build() (113-121), and Build (150-169) creates a GameObject with MeshFilter, MeshRenderer, CapsuleCollider, Rigidbody and CaseSound. WeaponSystem.OnSceneChanged calls Casings.DestroyAll() (src/Weapons/WeaponSystem.cs:802), which clears Alive and Idle (Casings.cs:294-316), so the pool is rebuilt from zero on each map.
  why:    Each build is roughly 0.1-0.3 ms (estimate). A revolver or break-action reload dropping 6-8 casings can add about 1-2 ms in one frame, and a full-auto gun builds one per shot until 40 exist. Small, and it happens once per map.
  change: Pre-build the 40 pooled case objects after the scene loads, at a quiet moment (for example from WeaponWarmup or the first frame after OnSceneChanged), so no shot or reload pays for Build().

  - WeaponRig.cs and WeaponOverrides.cs: no per-frame work. Overrides run per weapon analysis, and WeaponRig construction is cached per weapon. Casings.Cull and Spawn are O(40) pool operations.
