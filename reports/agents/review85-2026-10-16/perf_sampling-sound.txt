[major/medium] src/Weapons/SoundDonors.cs:73  Donor weapon fully analysed on the match frame that needs its sound
  what:   Donor() runs `data = WeaponAnalyzer.Get(w, e);` whenever the donor is not yet in `Donors` (SoundDonors.cs:46-85). Find() is reached from WeaponSoundPlayer.Play (WeaponSounds.cs:90) on every magazine or slide action (MechSound.MagOut/MagIn/SlideBack/SlideForward, SoundDonors.cs:23) of a weapon with no cue of its own (e.g. ReloadInteractions.cs:397, 1345). Get() -> Analyze -> SampleFromRigidBody -> PoseSampler.Run (WeaponAnalyzer.cs:3107-3108) steps the animator about 600 times and records up to 372 reload steps, all on the main thread.
  why:    The menu warm-up is the only place that pre-analyses weapons, and it is suspended for the whole match (WeaponWarmup.cs:121-124 and 134-137). If a match starts before the warm-up reaches the donor (RK-44, S-IND7, Automatico, Thumper), the first such action blocks the frame for the full analysis. The warm-up's own comment says one analysis is 'tens of milliseconds' (WeaponWarmup.cs:169), i.e. several dropped frames at 90 fps. It happens once per donor name per session, then the result is cached.
  change: In SoundDonors.Donor, after the allWeapons loop finds entry e and before the try at line 71, add `if (!WeaponAnalyzer.IsCached(w, e)) { return null; }` and do not add the name to Missing, so the warm-up fills the cache and a later action picks it up. Keys match (WeaponAnalyzer.cs:91-95 vs WeaponWarmup.cs:141), so the cached entry will be found. Optionally also put the donor names first in the warm-up order (WeaponWarmup.cs:114 PutLoadoutFirst). The same hazard exists at WeaponSystem.cs:344 (RigFor -> WeaponAnalyzer.Get) for an un-warmed weapon, outside this area.

[minor/medium] src/Weapons/PoseSampler.cs:441  Reload sampling re-reads the root and every transform's active state each step
  what:   RootRelative (PoseSampler.cs:438-442) reads _cloneRoot.rotation and _cloneRoot.position on every call, and Record (line 470) calls it for every transform. Visible (444-445) reads t.gameObject.activeInHierarchy and t.lossyScale, and Record calls Visible for every transform on each reload step (line 501). The audio-activation loop (lines 257-265) reads `_clone[i].gameObject.activeInHierarchy` for every transform on every step, although only transforms with _hasPlayOnAwakeAudio[i] use the result.
  why:    Reload sampling runs up to 372 steps (PoseSampler.cs:233-234: reloadTime clamped to 12 s, plus 0.4 s, at 30 Hz). Each step makes about 9-10 native transform or GameObject calls per transform, so about 3,700 x N calls for one long reload (about 220k for N = 60 transforms). This is most of the analysis cost that makes finding 1's hitch long. Analysis only, not per frame.
  change: (a) In Record, read the root once at the top: `Quaternion rootInv = Quaternion.Inverse(_cloneRoot.rotation); Vector3 rootPos = _cloneRoot.position;` and build each pose from them instead of calling RootRelative per transform. Nothing moves the root during the loop, so the result is identical. (b) In BuildClone, collect the indices with _hasPlayOnAwakeAudio into an int[] and loop only over those in the wasActive init (lines 246-249) and the reload activation loop (lines 257-265). wasActive only matters for those transforms. Both changes are behaviour-identical and remove roughly 40% of the native calls per reload step.

[tiny/medium] src/Weapons/PoseSampler.cs:720  Animation events re-fetched and collections re-allocated on every sampled step
  what:   EventTracker.Scan does `AnimationEvent[] events = clip.events;` (line 720) for each playing clip on every step. Collect allocates `new HashSet<AnimationClip>()` (line 678) and `new List<AnimationClip>()` (line 692) on every call.
  why:    Unity's AnimationClip.events getter returns a fresh array of new AnimationEvent objects with managed strings on each read (worth verifying against the Unity 2020.3 source). With about 470 steps and 1-3 clips per step, that is a few hundred KB of garbage per weapon analysis, feeding GC during menu warm-up. Analysis only.
  change: Cache the events per clip in a Dictionary<AnimationClip, AnimationEvent[]> on EventTracker, filled the first time a clip is seen. Keep `seen` and the stale list as fields and Clear() them at the start of Collect instead of allocating.
