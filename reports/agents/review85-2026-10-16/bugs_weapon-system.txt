[major/high] src/Weapons/WeaponOverrides.cs:66  Edits to weapons.json are never re-read after warm-up; live rigs stay stale
  what:   EnsureLoaded (WeaponOverrides.cs:49-86) is reached only through Apply(), and WeaponAnalyzer.Get returns the cached rig before reaching Apply (WeaponAnalyzer.cs:107-111; Apply is at :122). The comment at WeaponOverrides.cs:75-76 says edited weapons 'are analysed again (from their next draw)'. But WeaponSystem.RigFor (WeaponSystem.cs:340-346) keeps one WeaponRig per weapon instance in _rigs, and only a destroyed weapon (WeaponSystem.cs:221-240) or OnSceneChanged (:805-806) removes it.
  why:    WeaponWarmup analyses every installed weapon at menu time (WeaponWarmup.cs:110-158), so after that there is no cache miss and the file is never checked again. Editing RavenfieldVR.weapons.json during a session changes nothing, including on the next draw of the same gun, which still uses the old _rigs entry. The edit only takes effect after a restart or a later cache miss, so the documented live-edit path does nothing.
  change: Move the stamp check (EnsureLoaded) to the top of WeaponAnalyzer.Get, before the cache lookup. When the file changes, bump a generation counter in WeaponOverrides, clear WeaponAnalyzer's cache and WeaponWarmup's Warmed set (WeaponWarmup.cs:18). In WeaponSystem.RigFor, store the generation with each rig and rebuild the WeaponRig when it is stale. Also refresh the matching AmmoState, which holds its own Data reference (WeaponSystem.cs:410), or the ammo model keeps the old rig.

[major/high] src/Weapons/WeaponOverrides.cs:121  Action override leaves CyclesByHand from the detected action
  what:   Apply sets d.Action from the file (WeaponOverrides.cs:124-127) after analysis, but never recomputes d.CyclesByHand. That flag is derived only from the detected action: WeaponAnalyzer.cs:533-534 `d.CyclesByHand = d.Action == ActionType.Manual || d.Action == ActionType.ShellFed && !w.configuration.auto && w.configuration.cooldown >= 0.45f;` (also :225 in Fallback). Its readers use CyclesByHand, not Action: WeaponSystem.cs:421 (cancels the game's bolt/pump cycle on fire), ReloadInteractions.cs:1476 HandDriven (drives 1545-1577 and 3015), HeldWeapon.cs:926 (boltRifle).
  why:    The file's own example uses action = "Manual". On a self-loading gun that override gives Manual in name only: CyclesByHand stays false, so the game's fire animation keeps cycling the action and playing its sounds, and the reload is not hand-driven. The reverse, action = "SelfLoading" on a bolt gun, leaves CyclesByHand true, so the gun's own bolt is cancelled and worked by hand although the action says SelfLoading. The code fact is certain; the exact on-screen effect was not run.
  change: After setting d.Action in Apply, recompute d.CyclesByHand with the same expression as WeaponAnalyzer.cs:533-534. Put that expression in one helper (on WeaponRigData or WeaponAnalyzer) and call it from the analyzer's two places and from Apply, so they cannot drift apart.

[tiny/medium] src/Weapons/Casings.cs:232  Chambered round is centred on the port, not seated with its mouth at it
  what:   The comment at Casings.cs:230 says the case sits 'the length of a case back from its mouth'. The code at :232 puts the object origin, which is the case head (Lathe starts at z=0, Casings.cs:388-457), at `port.position - right * 0.004f - aim * mesh.bounds.size.z * 0.5f`.

[tiny/low] src/Weapons/WeaponRig.cs:391  AttachInGunSpace drops the sign of a mirrored gun body's scale
  what:   WeaponRig.cs:391 sets t.localScale to 1 / Mathf.Max(1e-5f, Mathf.Abs(s.x)) (and likewise y, z). The sign of GunBody.lossyScale is discarded.
  why:    On a mirrored rig (a negative scale on an odd number of axes) the attached child ends up with positive local scale, so its world scale is mirrored and asymmetric props (magazine, rounds) render inside-out. Only matters if a mod rig carries a negative scale.
  change: Keep the sign: `Mathf.Sign(s.x) / Mathf.Max(1e-5f, Mathf.Abs(s.x))`, and the same for y and z.
