perf ui-1 (Performance), read-only Haiku agent, 2026-10-16

SCOPE: Per-frame performance of the world-space UI (src/UI/CanvasManager.cs, UISystem.cs, VRInputModule.cs, LoadingView.cs, UiKit.cs, TextPlate.cs), read-only, nothing measured; magnitudes below are estimates from code reading. Verdict: in gameplay this area is cheap per frame. The hot loops allocate nothing per frame, and the GameContext getters are field reads. Its real costs are periodic full-scene searches (CanvasManager.Scan every 0.4 s; LoadingView.Capture every 0.25 s while loading) and the EventSystem raycast pass while a menu is up. Two TextPlate-based labels rewrite their TextMesh colour every frame. Not addressed: the user's m4a1 ACOG test question. It needs the game running, and this review cannot run anything. Other panel classes (VRSettingsPanel, ModKeysPanel, SquadPointing, WristHud, SeatSights) were only checked at their call sites.

[minor/medium] src/UI/CanvasManager.cs:156  Full-scene Canvas search every 0.4 s for the whole session
  what:   Update() schedules it: `if (Time.unscaledTime >= _nextScan) { _nextScan = Time.unscaledTime + 0.4f; Scan(); }` (lines 95-99). Scan() calls `foreach (Canvas c in UnityEngine.Object.FindObjectsOfType<Canvas>())` (line 156). ScanNow is also run inside BeforeRender (lines 402-407).
  why:    FindObjectsOfType walks the scene's objects and allocates a new array on every call. It runs 2.5 times a second during play and menus, so roughly one frame in 36 at 90 fps carries the full search on top of its normal work. Cost is unmeasured; my estimate is 0.5-2 ms in a populated match, which is a large share of the 11 ms budget on that frame. The ScanNow path also searches inside the render callback each time the loadout weapon list opens, but that is a one-off per open.
  change: Lengthen the periodic scan at CanvasManager.cs:97 from 0.4 s to about 2 s. Keep the forced scans that matter: OnSceneChanged already sets _nextScan = 0f and ScanNow covers menu opens. Confirm with a Profiler capture that the FindObjectsOfType<Canvas> sample appears once per scan and is gone after the change.

[minor/low] src/UI/VRInputModule.cs:115  EventSystem.RaycastAll runs every frame while a menu is up, across all raycasters
  what:   `_results.Clear(); eventSystem.RaycastAll(_data, _results);` (lines 114-115) runs from Process() every frame while PointerActive is true. Only the Targets list is intersected with the laser by IntersectCanvases (lines 175-207).
  why:    Unity's EventSystem.RaycastAll tests every active BaseRaycaster in the scene, not just the panels in Targets, and each GraphicRaycaster walks all the graphics on its canvas. If the game's HUD canvases keep active GraphicRaycasters (not verifiable from the decompile, which has no prefab data), they are walked too while the pause menu is up, though they are not laser targets. The cost then scales with on-screen graphics, not with the panels the laser can hit. My estimate is 0.05-0.5 ms per frame while a menu is up; unmeasured.
  change: Measure first: Profiler sample of EventSystem.Process with the pause menu open. If it is significant, while MenuMode is on set enabled = false on the GraphicRaycaster of each converted canvas whose role is Hud (CanvasManager already tracks the role), and restore it when MenuMode ends. Alternatively, call GraphicRaycaster.Raycast only on the Targets' raycasters instead of EventSystem.RaycastAll.

[tiny/medium] src/UI/LoadingView.cs:234  Loading scene searched for canvases and cameras every 0.25 s
  what:   Update() sets `_nextCapture = now + 0.25f;` (line 84) and calls Capture(scene) (line 85). Capture runs `foreach (Camera c in Camera.allCameras)` (line 214) and `foreach (Canvas canvas in UnityEngine.Object.FindObjectsOfType<Canvas>())` (line 234) on every call.
  why:    Four whole-scene searches a second for the length of the loading scene, each allocating arrays. The loading scene is smaller than a match and the screen is a blacked-out room, so a hitch costs less here than in play, but the frame loop still has to hold 90 fps for the compositor. The `_canvases` check at line 236 skips work only after the search has already run, so the search is the cost.
  change: Capture every ~1 s instead of 0.25 s, or only when the scene's root object count changes. Or search only the loading scene: `foreach (GameObject root in scene.GetRootGameObjects()) root.GetComponentsInChildren<Canvas>(true)` instead of FindObjectsOfType<Canvas>().

[tiny/high] src/UI/UISystem.cs:357  Laser colour string parsed every frame while the laser is shown
  what:   `Color c = VRConfig.ParseColor(VRConfig.LaserColor, new Color(0.91f, 0.71f, 0.29f));` inside LaserPointer.Update (line 357), which runs every frame the laser is shown. ParseColor (VRConfig.cs:456-458) calls `ColorUtility.TryParseHtmlString(entry.Value, out Color c)` each time.
  why:    A native hex parse about 90 times a second in menu mode. Microseconds and no GC garbage, but the value only changes when the config changes.
  change: Parse once: keep a Color field set in the LaserPointer constructor and refresh it when the config entry changes (or on a slow timer). Also assign `_material.color = Color.white` (line 372) only when it differs from the current value.

[tiny/medium] src/UI/UiKit.cs:50  One-time heap-wide Text search on the first font lookup
  what:   FindGameFont falls back to `foreach (Text t in Resources.FindObjectsOfTypeAll<Text>())` (line 50) when IngameMenuUi.instance has no Text (lines 42-49). The result is cached in _font (lines 30-33).
  why:    FindObjectsOfTypeAll walks every loaded object. It is one-time per session, but it lands on whichever frame first builds a panel (the UISystem constructor path), and it runs again if _font is destroyed by a scene unload (the `_font == null` check at line 30). Magnitude not measured.
  change: Warm UiKit.Font at a non-critical point (for example while the loading scene runs, or in the main menu), or drop the FindObjectsOfTypeAll fallback and take the font from one known game Text component instead of scanning all loaded Text components.

[tiny/high] src/UI/VRInputModule.cs:154  Hover lookup walks the hierarchy every frame while the laser is over an element
  what:   HoverTick runs every frame from Process() (line 130): `GameObject target = over != null ? ExecuteEvents.GetEventHandler<IPointerClickHandler>(over) : null;` (line 154). `_lastOver = over;` is set at line 128.
  why:    GetEventHandler walks from the hit object up the hierarchy, querying each ancestor's components for IPointerClickHandler, which is several native queries per frame. Tens of microseconds. The result only changes when `over` changes, and `_lastOver` already tracks that.
  change: Run HoverTick only when `over` changed: compare `over != _lastOver` before line 128 assigns `_lastOver`, and call HoverTick inside that branch. HoverTick's own `_hoveredTarget` check already makes this equivalent.

[tiny/low] src/UI/WristHud.cs:150  TextPlate labels rewrite TextMesh colour and refit the plate every frame
  what:   WristHud.cs:150 `_text.color = hp > 60f ? new Color(...) : ...;` and WristHud.cs:148 `_plate.Fit(); // every frame it shows`. The same per-frame colour assignment appears at AmmoCounter.cs:85, MagReadout.cs:110 and SquadPointing.cs:194, and Fit() is also called per frame at AmmoCounter.cs:73 and 86, MagReadout.cs:111, SquadPointing.cs:195. Fit() (TextPlate.cs:48-66) sets `_text.rotation = Quaternion.identity`, reads `_textRenderer.bounds`, then restores the rotation.
  why:    Fit costs tens of microseconds per visible plate (two transform writes and a bounds read). The larger risk is the colour write: TextMesh.color is a native setter, and if it marks the glyph mesh dirty even when the value is unchanged, every visible label rebuilds its text mesh every frame. I did not verify that from the code here.
  change: Assign _text.color only when the new colour differs from the last one set, the way the text itself is already guarded (WristHud.cs:142-147, AmmoCounter's _shown). Call _plate.Fit() only in the branch that changes the text and keep SetAlpha per frame. If the bounds lag a frame after a text change, set a dirty flag and Fit on the next frame.

CHECKED AND FINE:
  - CanvasManager.Update, BeforeRender and CollectVisible iterate Dictionary<Canvas,Tracked> and reuse the _dead, _targets and NestedBuffer/SelectableBuffer lists, so the hot loops allocate nothing per frame (struct enumerators).
  - GameContext.Player, InGame and GameMenuOpen are field reads: LocalPlayer.controller, GameManager.IsSpectating (GameManager.cs:1099), FpsActorController.IsCursorFree (FpsActorController.cs:1247) and the IsOpen() statics read a bool or enabled flag. Calling them several times a frame is cheap.
  - VRInput.Move, TurnStick and GetTrigger are cached static values, VRRig.Hands is a fixed array and Hand() is an index (VRRig.cs:44, 65), so the pointer path does no native work per call.
  - VRInputModule.RefreshCandidates rebuilds at most 10 times a second (VRInputModule.cs:214-225). IntersectCanvases runs twice a frame (VRInputModule.cs:101 via Process, UISystem.cs:260 via BeforeRender) over a few candidate canvases; tens of microseconds, accepted as intentional.
  - Classify (CanvasManager.cs:376-387) and GetComponentInParent<Vehicle> run at 2 Hz per visible canvas, not per frame. CollectFlat, ClipWithoutStencil and FlattenDepth run once per menu open or conversion.
  - EnsureModule's FindObjectOfType<EventSystem> (UISystem.cs:204) is throttled to 0.5 s and runs only while EventSystem.current is null.
  - CanvasManager.KeepFlat and the HUD placement in BeforeRender do only a few transform reads or writes per visible canvas per frame, and write only when a value is off.
  - LoadingView.Place is per-frame vector math only. During loading the rig camera's cullingMask is set to 0 (VRRig.cs:780-786), so no world geometry is rendered behind the loading screen.
  - UiKit's builders (MakeText, MakeButton, MakePanel) run at creation only; the button closure is allocated once, not per frame.
  - Not reviewed in depth (outside the file list): VRSettingsPanel.Refresh (called every 0.2 s while open from UISystem.cs:134-137), ModKeysPanel.Update (every frame, UISystem.cs:139), SquadPointing, SeatSights, WristHud beyond its TextPlate call sites.
