[minor/medium] src/Core/AutoTest.cs:248  A check that throws quits the game while a frame writer may still be encoding
  what:   WaitForMatch wraps the run as `yield return Safely(Run(), e => { Problem(...); Write(); Application.Quit(); });` (lines 242-249). Safely's catch calls `failed(e); yield break;` (274-277) and quits at once. The normal film path drains first: `for (...; EyeFilm.Writing > 0 ...) yield return null;` (351-355), with the comment 'quitting while a frame writer is in Unity's encoder crashed the game'. FlashFilm (673-879) has no try/finally around EyeFilm.Begin / film.Finish (754-864), so an exception between them (Cycle() at 803-809, Frames, CycleForTest) leaves the UI camera's EyeFilm recording and its writer thread running.
  why:    Any exception in a film gun (equip, Cycle, reload film) now takes the Safely failure path, which calls Application.Quit without the drain that a027999's own film path added. That is the crash the comment warns about, and the report is written from the same failure path. Application.quitting (lines 106-113) does not drain either.
  change: In Safely's catch, after failed(e), wait `while (EyeFilm.Writing > 0 && Time.realtimeSinceStartup < until) yield return null;` (30 s, as at line 351) before `yield break`, or make the failed action a coroutine that waits and then quits. In FlashFilm, wrap the gun body after EyeFilm.Begin in try/finally that calls film.StopRecording(), as ReloadFilm already does at 937-943.

[minor/high] src/Core/AutoTest.cs:1047  Lens-flash share records 1.0 for guns with no muzzle flash or that never fired
  what:   `Metric("lens flash check: share of shots that flashed (weapons with a muzzle flash)", expected && shots > 0 ? (double)flashes / shots : 1.0);`
  why:    A gun with no muzzle flash of its own (listed 'by design') and a gun that did not fire both add 1.0 to the metric, so the reported average and minimum are biased up and 'DID NOT FIRE' is hidden in the measurement. The label says only muzzle-flash weapons are counted. The per-gun Problem at 1052-1056 still catches real failures, so this hides a trend rather than a failure.
  change: Record only the guns the label describes: `if (expected && shots > 0) Metric("...", (double)flashes / shots);`.

[minor/medium] src/Core/AutoTest.cs:1552  Wrist-view open-time tolerance uses the longest frame of the whole window
  what:   `longestFrame = Mathf.Max(longestFrame, Time.unscaledDeltaTime);` runs for the whole 3.6 s window (1498), and the gate is `openedAt > 2.4f + longestFrame` (1552). Introduced in 9db2f56.
  why:    The ring fills on Time.unscaledTime (BodyZones.cs:171), so a hitch elsewhere in the window does not delay the fill. The only lag is detection: the gesture is seen one loop later, bounded by that frame's delta. A single 0.5 s hitch anywhere before the ring fills raises the upper bound to 2.9 s, so a ring that takes 2.8 s passes. The stated case (a 12 fps null driver) needs only about 0.08 s of tolerance.
  change: When openedAt is set (1509-1512), capture `openLag = Time.unscaledDeltaTime` for that detection frame and gate on `openedAt > 2.4f + openLag`. Drop the window-wide longestFrame.

[minor/medium] src/Core/EyeFilm.cs:151  Frame queue has no limit, so raw frames pile up in RAM when the writer lags
  what:   OnPostRender reads each eye's picture back every frame (EyeFilm.cs:144-146). The readback callback copies it into `new byte[w * h * 4]` (151-152) and enqueues it (155). `_queue` (line 32) is unbounded and the writer thread runs at BelowNormal priority.
  why:    A frame is about 0.8 MB (480 px wide, about 430 high, RGBA). Two eyes at 72-90 Hz is 150+ frames/s. FilmOneMag films a magazine on full auto until it is empty (AutoTest.cs:845-850, up to 40 s). The 120 s drain in Finish (EyeFilm.cs:85) shows the writer does lag, so one long burst can queue well over a GB before the game stalls or runs out of memory.
  change: Bound the queue. When Queued exceeds about 240, skip AsyncGPUReadback.Request for that frame, count the drops, and write a 'dropped' line into frames.txt so flashfilm.py keeps the frame index honest. Or shrink each queued item further (encode on the worker from the readback) so the cap is cheap.
