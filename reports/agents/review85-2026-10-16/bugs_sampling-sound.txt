[major/low] src/Weapons/PoseSampler.cs:138  Audio objects switched on by the fire animation are never sampled
  what:   The fire loop only does `StepOnce(Dt); ... Record(...); tracker.Collect(t, FireCues);` (lines 138-144). The audio-object scan (`_hasPlayOnAwakeAudio` and `wasActive`, adding `SampledCue { AudioObjectPath = ... }`) exists only in SampleReload (lines 256-265).
  why:    A sound carried by an AudioSource object that the fire clip enables never reaches FireCues, so it is missing from ShotCues. For CyclesByHand manual weapons the shot is then silent in PlayShotCues (WeaponSystem.cs:431). This depends on whether any mod rig uses a fire-clip audio object, which is why confidence is low. Note that BuildSoundMap bins fire cues after 0.1 s into SlideBack/SlideForward for manual weapons (WeaponAnalyzer.cs:2852-2858), so a later audio-object cue would be misfiled.
  change: Move the wasActive/_hasPlayOnAwakeAudio scan into a helper and call it in the fire loop after `tracker.Collect(t, FireCues)` (line 143), with `wasActive` captured before line 137. In BuildSoundMap, route AudioObject cues after 0.1 s to a shot-only list, not SlideBack/SlideForward.

[major/medium] src/Weapons/PoseSampler.cs:729  Animation event at a clip's time 0 is dropped on the step the clip starts
  what:   `float stepped = Dt * Mathf.Max(1f, Mathf.Abs(state.speed * state.speedMultiplier));` / `float from = hadPrevious ? prev : Mathf.Max(-1e-4f, now - stepped);` then `if (et > from && et <= now)` (line 740). The -1e-4 margin only matters when now - stepped < -1e-4; Max() keeps any value above it.
  why:    A clip that starts inside the step being scanned has now - stepped about 0, so from is about 0 and the strict `et > from` excludes an event authored at exactly t=0. Fire cues with Time <= 0.1 become ShotCues (WeaponAnalyzer.cs:2848-2850), which PlayShotCues plays for CyclesByHand weapons in manual reload mode (WeaponSystem.cs:426-431). A shot sound at frame 0 of the fire clip is therefore silent on bolt, pump and lever weapons. The same happens to a reload clip's first cue, which shifts MatchCues (WeaponAnalyzer.cs:2900) onto the wrong keyframes. Depends on whether the destination clip advances by dt in the transition's first update (Unity Mecanim believed to do so; not verified).
  change: Line 729: `float from = hadPrevious ? prev : now - stepped - 1e-4f;` so a clip's own start is inside the first window. Keep the `et > from && et <= now` test. Verify with the rig dump / self-test that a fire event at 0.000 s appears in ShotCues.

[minor/low] src/Weapons/PoseSampler.cs:233  Advanced reloads are sampled for the standard reload time
  what:   `float duration = Mathf.Clamp(config.reloadTime, 0.5f, 12f) + 0.4f;` applies to every reload. `config.advancedReload` only sets the motion (lines 218-229). The game advances advanced reloads on each motion's `MotionDone` (Weapon.cs:1299-1312) and chains motions through AdvancedReloadNextMotion (Weapon.cs:1267-1292), not on reloadTime.
  why:    If an advanced-reload motion runs longer than reloadTime + 0.4 s, the tail is not sampled, so keyframes like TMagIn and TSlideForward stay -1 (WeaponAnalyzer.cs:2804) and the manual timing is wrong. Only one motion is ever recorded, so a chained second motion (for example a bolt) is also missing. Depends on the weapon's config values.
  change: When `config.advancedReload` is true, size the window from the reload clip lengths on the animator (plus 0.4 s, capped at 12 s, or a fixed cap) instead of reloadTime alone. Check that TMagIn and TSlideForward are set for an advanced-reload weapon.

[minor/low] src/Weapons/PoseSampler.cs:711  Blend-tree child events use the state's time and a weight gate that resets tracking
  what:   `if (clip == null || info.weight < 0.3f || seen.Contains(clip)) continue;` (line 711), then the stale purge removes `_lastTime` for every clip not in `seen` (lines 691-703). Each clip's time is `float now = state.normalizedTime * length;` (line 717), which is the state's time applied to every clip in it.
  why:    A clip whose weight dips below 0.3 is purged and treated as first-seen on return, so events in the gap are dropped (only one step is scanned). For blend-tree states, state.normalizedTime is the tree's time, not a child's, so child events are placed at the wrong times and MatchCues binds them to the wrong keyframes. For single-clip states AnimatorClipInfo.weight is 1, so this only bites blend trees, which is why confidence is low.
  change: In Scan, update `_lastTime[clip] = now` for every clip with weight > 0 and gate only the event emission on weight >= 0.3, so the purge does not erase tracking of a clip still in the infos. For blend trees, time each child from its own length, or refuse to sample events from blend-tree states and log it.
