[minor/high] src/UI/SquadPointing.cs:347  Squad camera turn runs every frame, even with the squad menu closed
  what:   SquadPointUiByPointingPatch.Prefix (lines 341-351) calls `SquadPointing.Aim()` (line 347) and `SquadPointUi.SetDefaultText(...)` (line 351) before the canvas check on line 353. The game's own LateUpdate returns at once when the canvas is disabled (decompiled SquadPointUi.cs:176-178), but the Harmony prefix runs first, every frame. Aim (lines 119-147) moves the game's main and active cameras onto the pointing line whenever Pointing is true, and the postfix Restore (line 365) moves them back. Line 136 allocates `new[] { main, active }` on every call; line 355 calls `GetComponent<CanvasGroup>()` every frame the canvas is open.
  why:    Pointing is true whenever a hand is held roughly straight out, with the squad menu closed too. Then each frame: two camera transform writes, two restore writes, two accessor calls and a 40 B array (about 3.6 KB/s of garbage at 90 fps). The CPU cost is microseconds; the larger point is that the game's camera is moved and put back about 90 times a second when no order is being given.
  change: Return from the prefix before Aim/SetDefaultText unless `__instance.canvas != null && __instance.canvas.enabled`. The postfix Restore then does nothing. Replace the array on line 136 with two explicit calls or a reused field, and cache the CanvasGroup reference (or add it once). The order-issue path (SquadOrderByPointingPatch, line 321) keeps its own Aim call and is unaffected.

[minor/medium] src/Weapons/HolsterDisplay.cs:57  Holster copy destroyed and re-instantiated on each weapon change
  what:   BeforeRender (lines 57-66): when a spot's weapon changes, `Clear(spot)` destroys the copy (line 59; Clear body at line 227), then `Build` calls `WeaponDrops.ModelFor(entry)` (line 81), which does `UnityEngine.Object.Instantiate(template)` (src/Weapons/WeaponDrops.cs:134). Build then walks every transform (lines 95-98) and renderer (lines 99-119) with three InverseTransformPoint calls per renderer.
  why:    A pickup, or a switch that moves a weapon into a different holster spot, costs an instantiate and a full hierarchy walk on the main thread in that frame. Because the copy was destroyed, switching back repeats the whole cost. Rough estimate under 1 ms per event; not measured.
  change: Keep a per-entry cache of the Shown data (copy, Centre, Length, Frame) in HolsterDisplay, keyed by WeaponManager.WeaponEntry. On a spot change, SetActive(false) the old copy and reuse the new entry's cached copy. Instantiate and measure only the first time an entry is seen, or do it when the weapon is first picked up rather than at the swap.

[tiny/low] src/Weapons/HolsterDisplay.cs:72  Holster visibility has no hysteresis, so SetActive can toggle per frame
  what:   BeforeRender (lines 69-75): `bool visible = Vector3.Distance(centre, head.position) > 0.2f + s.Length * 0.25f || Vector3.Dot(head.forward, (centre - head.position).normalized) < 0.2f;` then `s.Go.SetActive(visible)`, using the same thresholds for showing and hiding.
  why:    A head held near a threshold can cross it on consecutive frames, toggling SetActive on a multi-renderer copy each time (visible flicker plus a per-frame activation cost, not measured). Low frequency.
  change: Give the two transitions separate thresholds (hide inside 0.2 + 0.25 * Length, show only beyond that plus about 0.05 m; or a dot-product margin of about 0.05), so the state changes once per real crossing.
