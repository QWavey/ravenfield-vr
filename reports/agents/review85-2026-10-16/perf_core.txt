[major/medium] src/Core/Log.cs:80  Log.Guard keeps retrying a section that throws every frame
  what:   Guard catches and returns: `catch (Exception e) { ExceptionOnce(context, e); }` (Log.cs:94). Nothing stops the next frame calling the same action. VRManager calls Guard up to 10 times a frame (VRManager.cs:142-145 Update, 187-188 LateUpdate, 197-208 OnBeforeRender). ExceptionOnce rebuilds `"guard:" + context + ":" + e.GetType().Name + ":" + e.Message` and takes a lock on every throw (Log.cs:41).
  why:    The code shows this has happened: VRRig.cs:400-401 says the quit-to-menu state 'throws every frame' and 'the hands froze', which means Rig.Update was aborted each frame inside Guard. While a section keeps throwing, every frame pays a managed throw/catch per section (tens of microseconds on Mono, more on deep stacks), a key string and exception allocations, and the rest of that section's work is skipped. If several sections throw together, the cost reaches a few tenths of a millisecond a frame, a few percent of the 11 ms budget (estimate).
  change: Add a per-context failure counter in Guard (Dictionary<string, GuardState> keyed by the literal context string, a few tens of ns per call). After 3 consecutive throws from one context, skip that context until Time.unscaledTime + 2 s, then retry. Reset the count on success. Keep the one-time log through ExceptionOnce.

[minor/high] src/Util/GameContext.cs:161  GameMainCamera throws and swallows an exception each frame in menus
  what:   `return GameManager.GetMainCamera();` inside try/catch(Exception) (GameContext.cs:159-166). GameManager.cs:392 uses `LocalPlayer.controller?.GetActiveCamera()`. `?.` tests only the C# reference, so a destroyed controller is still called, and FpsActorController.cs:1091-1095 reads `tpCamera.enabled` on a destroyed Camera. VRRig.Update calls DetermineMode every frame (VRRig.cs:285), which reaches FollowTarget (VRRig.cs:374). VRRig's own try (VRRig.cs:384-398) only covers its first branch, and when that yields null it still calls GameContext.GameMainCamera (VRRig.cs:407).
  why:    In the menu after a match (VR active, player destroyed), each frame throws one exception that the catch silently swallows, plus allocations. That is tens of microseconds and a few hundred bytes of garbage a frame, menu only, not during play. The VRRig fix at 386-401 is incomplete because its second branch reaches the same throw.
  change: At the start of GameContext.GameMainCamera, when `LocalPlayer.controller == null` (Unity null test), skip GameManager.GetMainCamera(): return the spectator camera if SpectatorCamera.instance and its camera exist and are enabled, otherwise Camera.main. Alternative in VRRig.cs:407: `cam = LocalPlayer.controller != null ? GameContext.GameMainCamera : Camera.main;`.

[tiny/high] src/Core/Log.cs:63  InfoOnce and WarnOnce build the key and take the lock before the once-check
  what:   InfoOnce (Log.cs:63-74) and WarnOnce (50-61) run `lock (Once) first = Once.Add(key)` after the caller has already concatenated the key. The success path at VRInput.cs:555 is `Log.InfoOnce("haptic-ok:" + h, ...)`, executed for every successful haptic pulse (VRInput.cs:549-556). The `h` enum is turned into a string on each call.
  why:    Every pulse after the first allocates a key string and performs an enum-to-string conversion before the set lookup. Pulses are event-driven, so the cost is about 100 bytes and under a microsecond per pulse. Real but tiny.
  change: At the caller (VRInput.cs:555), keep a bool per hand and call InfoOnce only while it is false. Or add a Log overload that takes a precomputed key so the caller can skip the concatenation.

[tiny/medium] src/Core/VRConfig.cs:456  ParseColor re-parses the laser colour every call; ParseVector caches
  what:   `return ColorUtility.TryParseHtmlString(entry.Value, out Color c) ? c : fallback;` (VRConfig.cs:458) with no cache, unlike ParseVector (413-427). Caller UISystem.cs:357 runs in Update(bool show, ...) (UISystem.cs:347) after the early return at 353-356, so it runs whenever the laser is shown.

[tiny/medium] src/Util/GameContext.cs:59  GameMenuOpen has no per-frame cache; ~20 callers re-read it
  what:   GameMenuOpen calls FpsActorController.IsCursorFree (FpsActorController.cs:1247-1254), which reads IngameMenuUi.IsOpen, LoadoutUi.IsOpen, StrategyUi.IsOpen, ConfigFlagsUi.IsOpen and ScoreboardUi.IsOpenAndFocused, each a Canvas.enabled or flag read.
