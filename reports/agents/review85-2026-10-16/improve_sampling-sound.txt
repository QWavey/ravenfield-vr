[major/medium] src/Weapons/ProceduralSounds.cs:112  Synthesised sounds ignore the weapon: one clip set and +-6% pitch for every gun
  what:   Play(MechSound sound, Vector3 position, float volume) sets src.pitch = UnityEngine.Random.Range(0.94f, 1.06f) at line 112 and plays one shared _clips[] built once in the constructor from fixed frequencies, for example Thump(t, 140f, 0.035f) for MagOut at line 26 and Ring(t, 1650f, 0.035f) for MagKnock at line 62. Nothing about the weapon reaches it.
  why:    Every action without its own or donor sound (Holster, DryFire, ShellIn, PinPull, Spoon, Pouch, MagKnock, MagScrape, MagLip, and MagOut, MagIn or slide on weapons with no donor) sounds the same on a pistol, a rifle and a belt-fed machine gun. A light polymer pistol magazine gets the same 140 Hz thump and ring as a heavy steel box, which makes guns feel toy-like or oversized.
  change: Add a pitchScale parameter (default 1f) to ProceduralSounds.Play and multiply it into line 112: src.pitch = pitchScale * UnityEngine.Random.Range(0.94f, 1.06f). In WeaponSoundPlayer.Play (WeaponSounds.cs:96) pass _rig.Data.IsPistol ? 1.12f : _rig.Data.IsMachineGun ? 0.9f : 1f, using the WeaponRigData fields at WeaponRig.cs:217 and 190. Optionally keep a second clip set with shorter decay for pistols and a longer, lower one for heavy guns, selected by the same flags.

[minor/low] src/Weapons/AudioSlicing.cs:57  Onset snap picks the loudest rise in a 250 ms window, not the one at the keyframe
  what:   Refine searches every frame from windowStart = keyTime - 0.25 (line 22) to keyTime + 0.15 (line 53) and keeps the single largest rise (lines 57-65), with no weighting by distance to the keyframe. The estimate the caller starts from is only 60 ms early (WeaponAnalyzer.cs:2882, start = Mathf.Max(0f, t - 0.06f)).
  why:    If the previous action's click sits 0.1-0.25 s before the keyframe and is louder than the real onset, the slice starts and ends on the previous sound, because the end is derived from the onset (lines 77-97). Fast magazine or slide sequences put keyframes 0.2-0.3 s apart, so this is the case that matters.
  change: Narrow the search to [keyTime - 0.08, keyTime + 0.12] and weight each rise by its distance to the keyframe: float w = 1f - Mathf.Abs(windowStart + f * FrameSeconds - keyTime) / 0.15f; float rise = (rms[f] - rms[f - 1]) * Mathf.Max(0f, w). Check the result on a real reload clip with the self-test before tuning further.

[minor/medium] src/Weapons/PoseSampler.cs:134  Fire cycle is sampled for only 0.8 s, so longer bolt or pump cycles are cut
  what:   const int fireSteps = 24; (line 134) at Dt = 1/30 s (line 29) records only 0.8 s after the trigger. WeaponAnalyzer.cs:1204-1206 derives TFireSlideBack and TFireSlideForward from that trajectory via SlideKeyframes, which leaves forward at -1 unless the slide returns inside the samples (WeaponAnalyzer.cs:1847-1873). WeaponAnalyzer.cs:2859 then uses d.TFireSlideForward >= 0f to choose nearForward.
  why:    For a Manual action (bolt or pump) whose slide is still moving at 0.8 s, TFireSlideForward is -1, nearForward is false, and every later cycle sound is labelled SlideBack (WeaponAnalyzer.cs:2860). The forward-stroke sound and its timing are lost for those weapons, which is the rack feel a player notices most on a bolt gun.
  change: Sample the fire cycle to its end instead of a fixed 0.8 s: raise the cap, for example const int fireSteps = 60 (2 s), or stop once the fire state has exited. The cost is trivial because it runs once per weapon during analysis. The premise (a bolt or pump fire clip longer than 0.8 s) is not verified from the assets, so check it with the existing self-test before relying on it.

[minor/medium] src/Weapons/WeaponSounds.cs:186  PlayRandom and PlayNext replay with uniform random picks, not the bank's rotation
  what:   PlayClip picks cue.Clips[cue.Clips.Length == 1 ? 0 : UnityEngine.Random.Range(0, cue.Clips.Length)]. The game's SoundBank.cs:46-56 does PlayRandom as lastIndex = (lastIndex + Random.Range(1, clips.Length)) % clips.Length, so it never repeats the previous clip, and PlayNext as lastIndex = (lastIndex + 1) % clips.Length, in order. ToCue (WeaponAnalyzer.cs:2979-2991) passes every bank clip for both functions.
  why:    With two or three bank variants, a replayed PlayRandom reload sound repeats the same clip back to back about one time in n (half the time with two clips). The game never does that, so it reads as a doubled click or stutter. PlayNext also loses its in-order cycling.
  change: Add public int LastIndex = -1; to SoundCue (WeaponSounds.cs:19-32). In PlayClip, when cue.Function is PlayNext set cue.LastIndex = (cue.LastIndex + 1) % n; when it is PlayRandom set cue.LastIndex = cue.LastIndex < 0 ? Random.Range(0, n) : (cue.LastIndex + Random.Range(1, n)) % n, and play that index. PlaySoundBank keeps its single clip. This mirrors the game's own rotation.
