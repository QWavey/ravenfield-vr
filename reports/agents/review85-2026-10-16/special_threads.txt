[minor/medium] src/Core/EyeFilm.cs:151  Readback queue has no bound: 518 KB per eye-frame accumulates when the writer lags
  what:   Each OnPostRender copies the frame into a new byte[w*h*4] (line 151, about 518 KB at 480x270) and enqueues it (lines 153-156) with no cap. The writer thread runs at BelowNormal priority (line 57). Finish() waits up to 120 s for the queue to drain (lines 85-88).
  why:    A film runs at up to two eyes times the game's frame rate. If PNG encoding is slower than that, the queue grows by tens of MB per second. A full magazine is about 1400 frames, so several hundred MB of managed arrays can build up, and the GC pauses land inside the frame-rate measurement the film is recording.
  change: In OnPostRender, before the AsyncGPUReadback.Request at line 145, return early when Queued > 16 (the lock-protected property at lines 102-111), and log a 'skipped' row into _frames. That caps the queue at about 8 MB and keeps the frame log honest.

[minor/medium] src/Core/EyeFilm.cs:196  Quit or scene unload mid-film leaves the PNG writer inside Unity's encoder during teardown
  what:   WriterLoop calls ImageConversion.EncodeArrayToPNG (line 186) on a background thread. OnDestroy (196-200) only sets _stop and signals _wake, and never joins the writer. Only Finish() (lines 89-94) drains and joins. AutoTest's Application.quitting handler (AutoTest.cs:106-112) only calls Write(), and the wait at AutoTest.cs:351-355 applies only to the flash-film path. Commit a2a4275 records that quitting while the writer was in Unity's PNG encoder crashed the game twice; it was fixed only for the Finish path.
  why:    If the game quits, or the EyeFilm component is destroyed by a scene unload, while frames are still queued, the writer keeps calling Unity's native encoder during teardown, which is the crash the fix was meant to prevent. Unity does not document ImageConversion.EncodeArrayToPNG as safe off the main thread (low confidence on that point; the crash evidence is the stronger argument).
  change: In OnDestroy, if _writer is alive, set _stop, call _wake.Set() and _writer.Join(5000). For the lasting fix, remove the Unity call from the worker: encode with a managed PNG writer (zlib via System.IO.Compression.DeflateStream plus CRC-32) that touches no Unity API, or encode on the main thread with a per-frame budget.

[minor/medium] src/Weapons/GunVolume.cs:536  Sync-readback path publishes the volume to the worker before its hull settings and OnReady are set
  what:   Build() runs the readback loop inline. When supportsAsyncGPUReadback is false (line 520), line 536 calls job.Arrived(index, ReadNow(rt)). On the last target that queues ThreadPool.QueueUserWorkItem (line 583), and the worker reads Volume.WantsHull (594), Volume.HullSlice/HullMaxPieces (597) and Volume.OnReady (601). The caller only sets those fields afterwards: For() sets v.WantsHull = true after Build returns (GunVolume.cs:263-266), Measure() sets HullSlice, HullMaxPieces and WantsHull after Build returns (lines 284-290), and WeaponDrops.cs:465 assigns v.OnReady = Keep after Measure returns, guarded only by a v.Ready check (line 459). There is no lock or barrier between the caller's writes and the worker's reads.
  why:    On a GPU or API without async readback, the worker can see WantsHull false, so HullPieces stays null and the hull is never fitted for held guns (HeldWeapon.cs:1260) or magazines (MagazineProp.cs:1122). Or it sees the defaults 0.03/16 instead of the requested 0.015/8. It can also read OnReady as null, so Keep never runs (WeaponDrops.cs:452-466) and the dropped weapon keeps its box collider. The async path is safe because every callback arrives on a later frame, after configuration.
  change: Give Build() an Action<GunVolume> setup parameter and invoke it on the new volume right after line 497, before the loop at line 521. Pass WantsHull, HullSlice, HullMaxPieces and OnReady through it, and delete the post-Build assignments at GunVolume.cs:266 and 288-290. In WeaponDrops.cs:447-466, pass Keep into Measure instead of assigning v.OnReady afterwards. For the cache-hit case, make the worker publish _ready and read OnReady under one lock, and have the registration method take the same lock and invoke the callback at once if already ready.

[tiny/high] src/Core/EyeFilm.cs:79  Finish gives up on pending readbacks after 3 s, so late frames are enqueued after the writer has exited
  what:   Finish waits only 3 s for _pending to reach zero (lines 79-82), then waits for the queue (85-88), then sets _stop = true (89) and joins the writer. The AsyncGPUReadback callback that is still outstanding enqueues its frame later (lines 153-157), after WriterLoop has returned (lines 174-180). The frame is never written, while frames.txt (line 95) already lists it.
  why:    A slow GPU readback at the end of a film silently loses its last frame(s). The frame log lists PNGs that do not exist, and Writing has already been decremented, so the autotest's wait ends early.
  change: Replace the 3 s loop at lines 79-82 with the same bounded drain as the queue loop, waiting while _pending > 0 || Queued > 0 for up to 120 s, before setting _stop at line 89.

[tiny/high] src/Rig/LensEffects.cs:603  Band thread can exit on _stop without signalling _bandDone, leaving the worker blocked forever
  what:   BandLoop checks _stop right after _bandWake[band].WaitOne() and returns (lines 603-606) without calling _bandDone[band].Set(). The worker waits on that event with no timeout (line 572, inside the finally at 568-574). Destroy() (lines 500-507) sets _stop and signals the band wake events, without joining anything.
  why:    If Destroy() lands in the gap between the worker's _bandWake[b].Set() and the band's stop check, the worker blocks forever on _bandDone[b].WaitOne(). That leaks one thread per LensEffects instance, and a new one is built each VR session (VRRig.cs:112). The threads are background threads, so the process still exits. The window is narrow, so likelihood is low.
  change: Change BandLoop line 605 to: if (_stop) { _bandDone[band].Set(); return; }. Optionally, have the worker wait with a timeout and re-check _stop, and join the worker thread with a short timeout in Destroy().

[tiny/low] src/Weapons/GunVolume.cs:498  _inFlight is incremented before code that can throw and is never decremented on that path
  what:   Interlocked.Increment(ref _inFlight) at line 498 runs before the foreach that calls ShapeFit.Readable(r) (lines 499-502) and before job.Volume and job.Left are set (503-504). If anything in that range throws, no readback is ever requested, so no Arrived() call decrements the counter.
  why:    InFlight stays above 4 for the rest of the session. WeaponWarmup.cs:130 then holds every weapon entry for its full 2 s waiting for it to drop, which slows the warm-up but does not hang it. It also leaks the temporary render textures from Render().
  change: Move the Interlocked.Increment(ref _inFlight) from line 498 to just before job.Volume = volume (line 503), after the _wantHull loop.
