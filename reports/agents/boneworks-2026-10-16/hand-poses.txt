Boneworks study (read-only Haiku agent, 2026-10-16): Boneworks hand poses and finger posing, from the decompiled IL2CPP class surface. Method bodies are interop stubs, so behaviour is inferred from field names, types, enums and signatures. Inferences are labelled.

MECHANICS
- Storage is per finger. Each finger has one base joint Quaternion (thumb1, index1, middle1, ring1, pinky1) and two distal curl values. In PoseData these are floats (thumb2/thumb3, index2/index3 and so on). In HandPoseData and LocalPoseData they are packed in a Vector3 (thumb23, index23 and so on). The thumb has the same shape as the other fingers. Extra fields are PoseData.cup (palm cup, inferred), angle and nativePry (the pitch/roll/yaw sample), and gripPoint and gripRotation.
- There are three pose formats. HandPoseData and LocalPoseData are flat single poses, used by the AI system and as the output of CapturePose. HandPose2 is the runtime pose space, a grid. Data.HandPose is a constraint asset with no finger data, which Grip references. All three share a name string (handPoseName, name, animationName) that works as the join key (inferred).
- The pose space is a grid. HandPose2.poseData is an array of PoseDataGroup, one per radius step (PoseDataGroup.radius). Each group has a neutral PoseData, six sample arrays along pitch, roll and yaw (positive and negative), and a poseArray. The runtime pose is therefore a point (radius, pitch, roll, yaw) inside sampled data, read with GetPitch, GetRoll and GetYaw(radius, index). The meaning of pitch, roll and yaw as hand orientation relative to the handle is inferred.
- Per-frame solve (HandPoseAnimator.SolvePose, from member names): DetermineMinMax picks the two bracketing radius groups and a blend factor t (_radMinIndex, _radMaxIndex, _radiusT). GenerateDataPoints builds a Vector3 point cloud for the group. CalculateWeights gives the weights of the current (pitch, roll, yaw) sample against that cloud (inferred scattered-data or simplex interpolation). BlendPose sums PoseData by weights, and quaternions are accumulated with QuatTimesFloat into a Vector4, which is a weighted quaternion average (inferred). RefreshRadius applies the radius blend to the weights. BlendOpenPose mixes the result with _openPose.
- Inputs to the solve: the grip radius comes from Grip.radius, goes through HandToGripState.poseRadius, and reaches the manager via SetCylinderRadius(handedness, radius). pitch, roll and yaw go in through ApplyPitchRollYaw(handedness, pitch, roll, yaw). The source of those three angles is inferred to be the hand orientation relative to the handle, computed from the GetHandleInHand* transforms.
- How a grip picks a pose: Grip.GetHandPoseTarget(hand) returns a pose name string. That string goes to SetHandPose(handedness, name) on HandPose2AnimationManager or CharacterAnimationManager (or SkeletonHand.SetHandPose(string)). The name resolves to a HandPose2, and the manager calls HandPoseAnimator.SetHandPose(pose, transitionTime). The exact name-to-asset lookup is not visible in the stubs. Per-hand overrides go through Grip.SetHandPose(Hand, HandPose) and RemoveHandPose. Per-hand state lives in HandToGripState (handPose, poseRadius, isFlipped). The handle placement table HandPoseHandleData.handleTransforms uses the same name as its key (inferred).
- Fade and transitions: HandPoseAnimator.SetHandPose copies the last applied PoseData into _transitionCache, resets _transitionFloat, sets _transitionTime from the optional argument, and stores the new target in pose. Update then advances _transitionFloat and LerpPose runs from the cache toward the new blended pose. A switch is therefore a timed lerp starting from wherever the hand currently is, not a snap (member names confirm the structure, behaviour inferred). Closing and opening use HandClose(perc) and HandCloseBlend(controller, blendPerc, closePerc), which mix open and closed reference hands by a 0..1 value.
- Per-finger timing: SubBehaviourHandPose.PoseFingerCurl takes thumbT, indexT, middleT, ringT and pinkyT and blends each finger between an open and a closed HandPoseData with its own parameter. The same class keeps _leftSnapshot, _leftTarget, _leftCurrent, _blendingWeightLeft and _deltaMultLeft, and steps at updateFps (inferred: snapshot-to-target blend at a fixed rate). HandPoseAnimator keeps per-finger _minX, _maxX and _currentX values, so each finger has its own clamp.
- Controller to finger curl: BaseController exposes GetIndexCurlAxis, GetMiddleCurlAxis, GetRingCurlAxis, GetPinkyCurlAxis and GetThumbCurlAxis (float per finger). OculusController and Controller compute these in ProcessFingers(), which writes _processed<finger> and _splay<finger> (finger spread) values. The _sim fields (_simIndexTouch, _simThumbAxis, _simGripAxisVive) look like simulated inputs for devices without the sensor (inferred). The index trigger analog is probably GetPrimaryInteractionButtonAxis, backed by _primaryAxis (inferred). Grip is GetGripAxis, GetGripForce and the solved _solvedGrip value from SolveGrip().
- Curl integration: FingerCurl holds fingers[5] (current values), overrides[5] and curlsPerSecond. Curl() moves each current value toward its target at no more than curlsPerSecond (inferred from the name). CurlOverride(thumb, index, middle, ring, pinky) writes explicit targets, probably used by scripted or gun grips (inferred). The five values then go to ApplyFingerCurl(handedness, thumb, index, middle, ring, pinky) on the manager or on SkeletonHand. They are stored as leftFinalFingerValues and rightFinalFingerValues and drive the open and closed finger reference transforms (inferred).
- No finger tracking: no skeletal finger-tracking types exist in this decompile (no OVRSkeleton, OVRHand, SteamVR_Skeleton, HandTracking or FingerTracking matches). Fingers are driven only by analog controller axes. OculusController.DrawSkeletonHand(Vector3[], Quaternion[]) is a draw helper (inferred).
- Gestures: BaseController.GetGesturePose(out poseIntensity, forceUpdate) classifies the hand into one of seven GesturePose values (OpenHand, IndexPoint, MiddleFinger, PeaceSign, ThumbsUp, ThumbsDown, Fist) with an intensity. It is refreshed on a timer (_nextGestureUpdateTime). Inferred use: picking an empty-hand or point pose.
- Thumb handling: the thumb has no special data shape (base quaternion plus two distal floats, like the other fingers). It is special in input and in clamping. It has its own GetThumbCurlAxis, _splayThumb, _processedThumb and _simThumbAxis. HandPoseAnimator has _minThumb, _maxThumb and _currentThumb. PoseFingerCurl has its own thumbT. The rig has separate Lthumb1 to Lthumb3 and Rthumb1 to Rthumb3 bones. ThumbsUp and ThumbsDown are dedicated GesturePose values, and ThumbsUp is a preset in SubBehaviourHandPose.HandPose.
- Hand placement: HandPoseTarget.GetHandRotationOffset(ControllerInfo.Type) gives a per-controller-model rotation offset (types UNDEFINED, OCCULUS_TOUCH, KNUCKLES, VIVE_WANDS, HOLOGRAPHIC). PhysHand.UpdateHand pulls a physics hand toward the controller target with forces and torques, with gripInput feeding SetFriction and RelaxTorqueMult. OverrideHand.MoveTo moves a transform at capped linear and angular speed (maxSpeed, maxAngularSpeed).
- Two-handed items: Grip.virtualControllerMode (GENERIC, HANDGUN, RIFLE, SLIDE, SLIDELOOK) selects a VirtualController routine (Gun, RifleShoulder, Slide, SlideLook) that computes the off-hand target. Grip.type (OVERRIDE, PRIMARY, SECONDARY) marks which hand owns the grip. The Pistol and PistolOffhand HandPoseData assets sit on SubBehaviourHandPose (AI side).
- Mirroring and flipping: HandPoseAsset.Mirror() and HandPose2AnimationManager.CopyLeft and CopyRight(out PoseData, angle, nativePry) build one hand's pose from the other (inferred). HandPose2AnimationManager.HandPose stores default and reverse position and rotation, and HandToGripState.isFlipped with flippedTargetRotation covers reversed grips (inferred).
- Other details: leftHandSpace and rightHandSpace are static quaternions (purpose inferred as a shared hand space). CoCalculateHandPoseRefs with isWarmup computes reference transforms over several frames at startup (inferred). Grip.handleAmplifyCurve and PhysHand.TorqueMultiplier are AnimationCurve fields, so response shaping uses curves rather than linear values. EnemyPoseData (StressLevelZero.Data) holds per-bone position and rotation arrays and is not hand-specific.
- Name collision: StressLevelZero.Data.HandPose (grip constraints), SubBehaviourHandPose.HandPose (enum) and HandPose2AnimationManager.HandPose (struct) share the name HandPose. Grip.cs imports StressLevelZero.Data, so Grip's HandPose is the constraint asset.

LESSONS
- Store each pose per finger (base quaternion plus distal curl floats), as PoseData and HandPoseData do. That lets the thumb move independently of the four fingers.
- Thumb slide-off then push: give the thumb its own blend factor and its own timer, longer than the fingers (compare PoseFingerCurl thumbT). The thumb can then lift off the mag slowly and ease into a push pose while the other fingers stay on their own schedule. Give the thumb its own clamp as well (compare _minThumb and _maxThumb).
- Fade, never snap: when the target changes, snapshot the currently applied pose (compare _transitionCache) and lerp from that snapshot to the new target over a duration (compare _transitionTime). If a new target arrives mid-fade, re-snapshot the in-flight pose rather than the old target (compare _leftSnapshot and _leftTarget). This answers the request for double-mag reloads to fade rather than switch abruptly.
- Fade out to open: blend toward an open pose instead of a separate release pose (compare BlendOpenPose and HandClose(perc)). Drive the whole blend from one 0..1 closedness value, so the trigger or grip axis, or the mag state, can fade the hand smoothly.
- Rate-limit finger motion: move each finger toward its target at a capped speed (compare FingerCurl.curlsPerSecond). Use a lower cap for the thumb to get the slow slide-off, and reuse the same mechanism for the closing motion of the mag grab.
- Use an override channel: let scripted reload gestures write explicit finger targets (compare CurlOverride and overrides) and release back to controller input with a fade, rather than disabling input entirely.
- Use an animation curve for the ease (compare Grip.handleAmplifyCurve and PhysHand.TorqueMultiplier) rather than a linear t. An ease-in suits the thumb lift and an ease-out suits the push.
- Blend rotations as quaternions (weighted sums with normalisation, compare QuatTimesFloat), not Euler lerps, when mixing grips or reload poses.
- For a continuous mag grab, derive the pose from how the hand wraps the mag (a radius plus wrap angles) and interpolate across sampled radius groups, as HandPose2 does. Only do this if the pose needs to vary continuously. Otherwise a few discrete poses with a blend between them is simpler.
- Mirror the offhand: author the pose once and mirror it for the second hand (compare HandPoseAsset.Mirror and CopyLeft and CopyRight) for double-mag reloads.
- Key every pose by a name string shared between the grip constraint, the pose data and the handle placement (handPoseName, name, animationName). Then the mag-grab, push and reload-hold poses can be swapped with one key.
- Add a per-controller-model hand rotation offset (compare HandPoseTarget.GetHandRotationOffset with ControllerInfo.Type). Otherwise the grip sits differently on Touch, Index and Vive controllers.
- Use the gesture classifier idea (GesturePose with intensity) to decide when the empty hand should push, for example from ThumbsUp, OpenHand or Fist states with an intensity, instead of ad hoc button checks.
- If several weapons solve poses every frame, run the solve at a fixed rate and interpolate between results (compare SubBehaviourHandPose.updateFps).
