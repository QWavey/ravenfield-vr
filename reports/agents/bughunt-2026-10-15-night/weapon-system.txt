2. [PLAUSIBLE] [minor] Nearest() runs ClosestPoint on every collider of every drop each frame
   src/Weapons/WeaponDrops.cs:740
   what: Nearest(palm) runs every frame for each grab-capable hand (WeaponDrops.cs:578-579). It calls c.ClosestPoint(palm) on every collider of every dropped weapon, with no bounds or distance pre-check. Drop shapes are up to 16 convex MeshColliders each (ShapeFit.Fit default maxPieces 16 at GunCollider.cs:525, and 12 in FitModel), and MaxDroppedWeapons defaults to 16 (VRConfig.cs:286). The result only matters for colliders within PickupReach (0.11 m).
   trigger: On foot with a dozen or more drops on the ground (common after a firefight at the default cap) and both hands tracked and free: up to about 16 drops x 16 pieces x 2 hands = 512 physics closest-point queries per frame. The cost is not measured here.
   fix: Before the collider loop, skip a drop whose transform is farther from the palm than PickupReach plus its bounding radius, and inside the loop test c.bounds (or a bounds squared-distance) against PickupReach before calling ClosestPoint.
   skeptic (correct): not real, medium: The call pattern in the finding is accurate. WeaponDrops.cs Update() (554-593) calls Nearest(hand.Palm.position) for each tracked hand that can grab, on foot, with drops present and the menu closed. Nearest (728-749) loops over every drop and every collider and calls c.ClosestPoint(palm) with no bounds or distance pre-check and no early exit. The drop colliders are convex MeshColliders (ShapeFit.AddColliders, ShapeFit.cs:603-604), and the selection threshold is PickupReach = 0.11 m (line 57).

The result is correct. ClosestPoint on a convex collider gives the nearest surface point, and the code keeps the nearest drop strictly under PickupReach. No wrong or missed pickup can come from the current code, and the finding itself says the result only matters within PickupReach. The issue is speed only.

Counts checked: Cull (804-845) caps non-owner drops at MaxDroppedWeapons (default 16). Owner drops are uncapped but are few. The spawn path (FitModel, line 513) uses maxPieces 12. The held-drop path uses GunCollider.Fit (default 16, GunCollider.cs:525) and appends up to 8 magazine pieces (WeaponDrops.cs:916-922), so one drop can have up to 24 pieces. The worst case is about 16 x 24 x 2 = 768 queries, not 512.

The trigger is also broader than stated: canGrab (line 578) is true for the dominant hand in the Weapon or Throwable role, so "both hands free" is not required.

The per-query cost is not measured anywhere in the repo, and nothing in the code shows it is material. The proposed bounds pre-check would be valid and cheap, so it is a reasonable optimization. But this is an unmeasured efficiency concern with no correctness consequence, so it does not meet the bug bar under a correctness lens. Confidence is medium because the call is partly a judgement about whether the cost counts as a bug.
   skeptic (reach): REAL, medium: The code path is as described. Update() (WeaponDrops.cs:554-593) runs every frame via WeaponSystem.Update (WeaponSystem.cs:137). It returns early only if the player is not on foot, a menu is open, or there are no drops. For each tracked hand with canGrab (Free role, or the dominant hand holding a weapon or throwable), Nearest(palm) is called (line 579). Nearest (lines 728-749) loops over every drop and every collider in d.Colliders and calls c.ClosestPoint(palm) with no bounds or distance pre-check. So the cost is O(drops x pieces) per hand per frame, as claimed.

Reachability: EnemyWeaponDrops defaults to true (VRConfig.cs:283), DroppedWeaponLifetime is 90 s (line 285), and MaxDroppedWeapons is 16 (line 286). Cull() (lines 804-845) caps non-owner drops at that number, so 16 bot drops in a 90 s window after a firefight is plausible. Free hands on foot are the normal state, so both hands can scan at once.

Piece count is overstated. Bot drops are built in Spawn -> FitModel (WeaponDrops.cs:513 and the rendered-shape path at line 443), both with maxPieces = 12, not 16. The 16 default (GunCollider.cs:525, ShapeFit.cs:78) applies only to the player's own DropHeld weapons (WeaponDrops.cs:898). Those are not counted against MaxDroppedWeapons, but there is at most about one per loadout slot. Worst case per frame is therefore about 16 x 12 x 2 = 384 ClosestPoint calls for bot drops, plus a few owner drops at 16 pieces each, not 512 from a uniform 16-piece count. Each call is a native query on a small convex hull (up to 180 hull points, ShapeFit.cs:297), which I expect to be well under a microsecond. Total cost is plausibly a fraction of a millisecond per frame, but I could not measure it. The reporter's own note says the same.

Verdict: the mechanism and trigger are real, so this is a real but minor performance issue, not a functional defect. A player would not normally notice it. The suggested fix is valid: c.bounds is a conservative world-space AABB, so testing its distance against PickupReach before ClosestPoint cannot skip a collider that would have been within reach.

   what: The in-match guard (lines 121-124) runs before each entry.    trigger: GunVolume.InFlight is above 4 (read-backs from MeasureRenderedShape still pending) and the player starts a match during the up-to-2 s wait. One analysis of tens of milliseconds then lands at the start of the match. This needs several volumes in flight at once, so it is rare.
   fix: After the InFlight wait loop, re-check the match before the Warmed test at line 137, e.g. `while (InMatch()) yield return new WaitForSecondsRealtime(1f);`.
   skeptic (correct): REAL, high: The mechanism is real. In src/Weapons/WeaponWarmup.cs the in-match/menu-use guard (lines 121-124) runs once per entry, before the GunVolume.InFlight wait (lines 130-133). That wait yields one frame at a time for up to 2 s and has no re-check afterwards. The analysis (lines 137-158: WeaponAnalyzer.Get, PrefitShape, WeaponDrops.Prepare, sub-weapon analysis) runs unconditionally after it. I found no other guard on that path: WeaponAnalyzer.Get (line 104) has no IsIngame check, and grep shows the only IsIngame/InMatch uses in src/ are in WeaponWarmup.cs and AutoTest.cs.

The coroutine survives a map load. VRManager's host object is DontDestroyOnLoad (src/Core/VRPlugin.cs:52), so Run() keeps going once the map scene is active. InMatch() is GameManager.IsIngame (decompiled GameManager.cs:463), which is buildIndex > 2 for normal levels. The game loads maps through the loading scene (buildIndex 2, IsInLoadingScreen) with LoadSceneAsync (LoadingScreen.cs:296-302), so the warm-up keeps running during loading, and "match start" means the map scene activates. If that activation happens inside the up-to-2 s InFlight wait, the analysis runs in the match's first moments. Once it has run, Warmed is set and the next entry's top guard catches the match, so the leak is one analysis per occurrence, not a repeating one. Impact is a single hitch, consistent with "tiny".

Frequency is the weak part of the report. The "several volumes in flight, so rare" premise is not established. The warm-up's own WeaponDrops.Prepare -> MeasureRenderedShape creates volumes for every unreadable mesh (ShapeFit.Readable), and their in-flight count drops only after the worker-thread FitCloud finishes, which the pacing does not wait for. With many such weapons, InFlight > 4 may be a common state, so the rarity rests only on the scene activation falling inside the wait. That is plausible, not negligible.
