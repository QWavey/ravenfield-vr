1. [PLAUSIBLE] [major] Reload-hand grasp offset mixes root-relative palm with gun-relative wrist
   src/Weapons/WeaponAnalyzer.cs:1193
   what: graspOffset = PalmOf(hand, sampler) - sampler.RelIdle[hi].position subtracts a gun-body-relative wrist position from a root-relative palm position. PalmOf returns sampler.Idle(...) positions, which are root-relative (PoseSampler.RootRelative, PoseSampler.cs:433-437, used by CaptureIdle at :445). RelIdle (PoseSampler.cs:452) and the ReloadTrajectory samples used as traj[a] (PoseSampler.cs:484) are gun-body-relative. The error equals the gun body's offset from the weapon root, so every grasp start in the stroke search is shifted by it. The shifted start feeds the offBore <= 0.16 and alongBore window filters (lines 1196-1204), and the stroke's bestStart becomes RackPoint. Lines 710, 720 and 1632 convert PalmOf correctly, which makes this line the outlier.
   trigger: A rifle with no bolt part of its own (bolt baked into the receiver, so RackStrokeFromHands is the rack source) whose gun body is a child of the weapon root at a non-zero offset. The true reload-hand stroke is rejected or a displaced one is accepted. When the result is used, HeldWeapon.SnapRackPoint (HeldWeapon.cs:1231-1246) sees a surface offset above 0.05 m and replaces the whole reload-hand rack with RackEstimate, so the hand never takes the bolt where the reload hand does.
   fix: Vector3 graspOffset = gunIdle.InverseTransformDirection(PalmOf(hand, sampler) - sampler.Idle(hand).position); (gunIdle is already a parameter of RackStrokeFromHands, line 1179).
   skeptic (correct): REAL, high: Checked the frames on the path the finding names.

1. PalmOf (WeaponAnalyzer.cs:3296-3310) returns sampler.Idle(...) positions. Idle() returns _idle[i], which CaptureIdle fills with RootRelative(...) (PoseSampler.cs:441-445, RootRelative at :433-437). So PalmOf is in the weapon-root frame.
2. RelIdle[i] = gunInv.Multiply(_idle[i]) (PoseSampler.cs:452), with gunInv = _idle[gun].Inverse(). Algebra per RigidPose (OpenVRMath.cs:59-71): RelIdle.position = q^-1 (wrist_root - g_p), i.e. gun-body frame, where q and g_p are the gun body's rotation and position in root space.
3. ReloadTrajectory samples come from Record (PoseSampler.cs:459-490): trajectory = gunInv_k.TransformPoint(pose.position), so they are gun-body-relative, the same frame as RelIdle and as d.MuzzlePoint/AimAxis/GripPoint (all gunIdle.InverseTransform... at WeaponAnalyzer.cs:502-511, 710, 720).
4. Line 1193: graspOffset = palm_root - wrist_gun. Line 1196: start = traj[a] + graspOffset is then gun-frame plus a mixed-frame offset. Error = palm_root - palm_gun = palm_root - q^-1(palm_root - g_p). With q = identity this is exactly g_p, the gun body's offset from the root, as the finding says. The error is generally larger when the gun body is also rotated relative to the root. At idle the start equals palm_root coordinates read as gun coordinates.
5. The suggested fix is algebraically correct: q^-1(palm_root - wrist_root) = palm_gun - wrist_gun, and gunIdle is the same pose as RelIdle's reference (both are _idle[_gunIndex], gunBody is updated by ref in SampleFromRigidBody and gunIdle is read after it, WeaponAnalyzer.cs:494).
6. Consequence path: start feeds the offBore <= 0.16 and alongBore filters (1201). bestStart becomes RackPoint (1247 or 1255), and RackFromHand is set on the no-SlidePath branch (1253). HeldWeapon.SnapRackPoint (HeldWeapon.cs:1228-1265) uses that point: if the surface distance is above 0.05 and RackFromHand is set it swaps in RackEstimate (1238-1240). Below 0.05 the displaced point is still moved onto the surface and written to RackPointGun, so the displacement persists. Nothing between 534 and the snap resets RackPoint, FinishVirtualParts (2792) skips because RackFromHand is set, and BoltInsideOnSurface (633) returns early on RackFromHand.
7. Not a root-frame/gun-frame mix in the other call sites: lines 710, 720 and 1632 convert PalmOf correctly, as the finding says.

What limits reachability: the error is zero when the gun body has the root's exact pose (for example gunBody == root, or an identity child). It needs a real non-identity gun-body pose, which I cannot verify without the weapon assets, so the magnitude per weapon is data-dependent. Also, NamedChargingHandle (WeaponAnalyzer.cs:570-624, called at :536 after :534) does not check RackFromHand and overwrites RackPoint at :617 when a named handle part exists, so the bug is only visible when no named charging handle is found.
      correction: Real as described; the mechanism and suggested fix check out. Refinements: (1) the error is palm_root - q^-1(palm_root - g_p), where q and g_p are the gun body's rotation and position in the weapon root. It equals the gun body's translation offset only when the gun body's rotation relative to the root is identity; a rotated gun body (common in exported rigs) gives a larger error that grows with the palm's distance from the root. (2) The effect is not limited to the >5 cm RackEstimate fallback: any nonzero error shifts RackPoint and the window filters, and SnapRackPoint moves the shifted point onto the surface, so the rack point stays displaced by the error even when it is under 5 cm. (3) The trigger should also exclude rigs with a named charging handle part, since NamedChargingHandle (WeaponAnalyzer.cs:617-620) overwrites RackPoint and RackFromHand afterwards.
