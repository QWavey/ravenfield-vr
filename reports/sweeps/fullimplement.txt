1. Skill: FULL IMPLEMENT - autotest checks that report but never fail
Where: src/Core/AutoTest.cs:3448, 3461, 3835, 3850, 3918, 3946, 4073, 4138, 4166, 4233, 4267, 4347, 4402, 4466, 4581,
4656, 4795, 4858, 4896, 4929 (soldier skips); 1843, 2325, 2414, 2608, 2643, 993, 1254 (Results-only skips); verdict at
6806 (Failure regex), 381, 1184, 6636 (where lines become problems), 6944 (the final count).
Quote (line 3850): report($"soldier grab: skipped (the soldier could not be brought: {broughtNote})");
What is wrong: A skipped check is only a text line. A problem is added only when a line matches the capitals-only Failure
regex (line 6806: \b(NOT|NOTHING|NO|NEVER) [A-Z]|TOO SMALL|...). "could not be brought", "skipped (off hand ...)" and
"skipped (no player)" never match, so they never count. The deploy failure is the one skip path that was fixed (line 323-324
calls Problem() and says why). The lower-case "physics shape: the rendered-model fit was not kept" (line 3129) is a
failure-type line that also does not count.
Trigger and effect: The soldier suite (18 skip sites) runs only if a bot is brought within 1 m of the spot in 0.6 s (Bring,
lines 3586-3594). If that fails, or the off hand holds something at 3445-3447, every soldier check skips and the run still
ends with "Autotest finished: N problems" (line 6944) where N can be 0. The same is true of the five environment checks
(standing still, wrist view, pause menu, loadout list, squad pointing). A run that passes can have tested none of the
soldier grabs, throws, neck, shield or punch checks.
Proposed change: One helper, Skip(string name, string reason), that adds the line to Results, counts it, and keeps the
names. Write "Skipped: N (names)" beside "Problems" in the report file and in the Log.Info at line 6944. In a full run treat
a skip of a required check (soldiers, environment, deploy-like cases) as a problem, as line 324 already does for deploy; keep
-rfvr-quick and genuinely optional skips (no second weapon, no grenade in the loadout) as information. Add the skip phrases to
tools/tests/failure_phrases_test.py so this cannot reopen silently.
How sure: high (the verdict paths and skip lines were traced; the exact count of runs that hit a skip is not measured).

5. Skill: FULL IMPLEMENT - open Tasks.md item buildable without the game, and a fixed-size design that only fits one machine
Where: src/Rig/LensEffects.cs:107 (Bands = 4), :109-112 (per-band threads and events), :157 (wash scratch per band),
:231 (worker AboveNormal), :232-238 (band threads created whatever the core count); docs/Tasks.md:1409 (open, "[minor, lens]").
Quote (LensEffects.cs:107): private const int Bands = 4;
What is wrong: The flash picture is cut into four fixed bands (the top and bottom half of each eye), and one thread per band is
started regardless of the machine. Environment.ProcessorCount is not read anywhere in LensEffects.cs. Band 0 runs on the
worker and bands 1-3 on their own threads, so on a four-core CPU the worker plus three bands are busy at once beside Unity's
main thread; on eight or more cores the bands sit idle while the band that holds the muzzle's starburst (usually the one below
the lens middle, Tasks 1409) finishes last.
Trigger and effect: Every flash, hit, low-health or drops frame waits for the slowest band (Tasks estimates it at 1.3 to 1.6
times the mean), so the picture arrives later. On fewer cores the threads compete with the main thread. The output does not
change, so there is no visual risk.
Proposed change: Split each eye's picture into 12 to 16 row strips; let the worker and the band threads take strips from one
shared counter with Interlocked.Increment; size the thread count from Environment.ProcessorCount (for example min(3,
ProcessorCount - 2), at least 1); give each thread its own wash scratch instead of indexing _washX/_washY by band. The output
stays identical, so before the in-game check compare the Color32 arrays of a fixed job rendered with one thread and with four,
offline if the job can be built without Unity's scene.
How sure: medium (the code state is verified; the speed-up is the Tasks estimate, not measured).
