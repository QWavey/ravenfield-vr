1. [OPTIMIZE] src/Input/VRInput.cs:265-273, the per-hand digital loop in Update(); the slot mapping is at VRInput.cs:907-923.
Quote: "bool ok = input.GetDigitalActionData(DigitalHandle[a], ref data, DigitalSize, HandSource[h]) == EVRInputError.None && data.bActive;"
What is wrong: every frame the loop reads all 18 digital actions for both hands (36 SteamVR calls). Ten actions are never queried with a hand argument anywhere in src: FireMode, Sprint, WeaponNext, Kick, Loadout, Scoreboard, Pause, VRMenu, Countermeasures, ModKeys. They are read only through the any-hand slot, so their 20 per-hand reads feed nothing except the OR at VRInput.cs:306. Map must stay per-hand: Slot() (VRInput.cs:919-920) sends MagRelease's per-hand reads to Map's index while the weapon is in the other hand, and MagRelease has five per-hand callers.
Trigger or user-visible effect: 20 SteamVR calls a frame are wasted; no visible effect today.
Saving: 20 calls x 1.2 us = about 0.024 ms a frame (Tasks.md:549 measured 0.060 ms for about 51 calls). If the current 0.16 ms Input section implies about 3 us a call, it is about 0.06 ms.
Proposed change: for those ten actions, read once with OpenVR.k_ulInvalidInputValueHandle as the any-hand state and skip the two per-hand reads. The dropout handling must come with it: the comments at VRInput.cs:261-264 and 483-484 say a per-hand dropout re-pressed Pause, FireMode and Sprint, so these actions need the HandOutage/HeldBeforeOutage path kept, or a headset dropout test before the change lands.
Confidence: high that the 20 calls have no caller; medium on the time saved; medium overall because the dropout behaviour is the risk.

5. [OPTIMIZE] src/Rig/HandModel.cs:1333 (SolveFinger, the final bisection step), exact duplicate work.
Quote: "int hit = FirstTouch(f, c0 + (n0 - c0) * hi, c1 + (n1 - c1) * hi, c2 + (n2 - c2) * hi, in0, in1, in2);"
What is wrong: after the five-step bisection (HandModel.cs:1320-1332), the FirstTouch at hi recomputes a result already known. Either hi was set by a probe at that exact value (the branch at 1324-1331), or hi is still 1, and then the same arguments were tested at HandModel.cs:1312 and returned touching, because this branch only runs on a touch. Each repeat costs one Chain (three AngleAxis products and matrix multiplies) and up to nine Solid tests.

Proposed change: keep the FirstTouch result from the touching probe (the one that set hi, or the result from line 1312 when hi is still 1) and use it as hit. The output is identical; there is no behaviour change.
Confidence: high (exact, same output); the saving is small.

6. [OPTIMIZE] src/Rig/HandModel.cs:1157-1179 (PalmOffset), called from SettlePalm at HandModel.cs:1144-1146 when the grip moved, a slide is in progress, or the target is unset.
Quote: "for (float o = 0.002f; o <= 0.0201f; o += 0.002f)"
What is wrong: the scan tests PalmTouches at each 2 mm step out to 2 cm, and at 0 and then on the negative side out to -4 cm. The palm skin has 12 points (HandShape.cs:131-135), so one PalmTouches is up to 12 Solid tests. Worst case is about 31 PalmTouches, about 370 Solid tests, on one frame.
Trigger or user-visible effect: only frames where the hand moves on the grip or a slide is in progress; usually only a few probes, because the scan returns at the first clear offset.
Saving: up to about 5 us a frame on those frames.
Proposed change: start the scan from last frame's answer (_palmTarget) and step outward by 2 mm both ways, so a steady hand takes 2-3 probes. This is not identical: contact is not always monotone along the palm normal, so the answer can differ on a concave part. It needs the grip check the comment points at (tools/hands/grip_check.py, named at HandModel.cs:497) before it lands.
Confidence: medium on the cost; low on whether it is worth the behaviour risk.
